# Rainy architecture

Rainy is one Windows desktop application written in Rust: the interface, `RainyAgent.exe`, is drawn with GPUI, and the backend, `rainy-host`, runs where the user's files are. Since 4.1 no part of Rainy runs on Node.js. Documents the interface does not draw itself are React pages shown in WebView2. There is no plugin framework: every part is a plain module that `native/crates/app/src/main.rs`, `native/crates/host/src/main.rs` or `src/renderer/main.tsx` constructs explicitly.

## Processes

```text
RainyAgent.exe (native/crates/app + carrier)   window and interface (GPUI), updates, optional modules, Strata, WSL setup, SSH targets
  │  spawns over stdio (RAINY_CONTROL lines)
  ▼
rainy-host, one per execution target: rainy-host.exe on Windows, rainy-host inside a WSL distro or on a Linux server over SSH
  │  HTTP + WebSocket on 127.0.0.1:<random port>, launch-token cookie
  ▼
RainyAgent.exe connects to /rpc; WebView2 panes load the viewer pages (src/renderer/viewer) from the same origin
```

The Cargo workspace in `native/` has four crates:

- `rainy-protocol` (`crates/protocol`): the types of the `/rpc` protocol and the streaming patches, shared by the Host and the interface. `src/shared/rpc.ts` holds the TypeScript side the viewer pages use.
- `rainy-host` (`crates/host`): the Host, built for Windows and, with `cargo-zigbuild`, for x86_64 Linux with glibc 2.17 (`native/scripts/build-hosts.sh`).
- `rainy-carrier` (`crates/carrier`): what Electron main did in 3.x. It starts the Host for an execution target, answers its control requests, connects to `/rpc` and the language-server sockets, and owns the credential key (DPAPI), the system proxy lookup (WinHTTP), SSH and its askpass, WSL setup, optional modules, the Strata engine, signed resources, updates, single instance, the window state and the Explorer integration.
- `rainy` (`crates/app`, built as `Rainy.exe` and installed as `RainyAgent.exe`): the GPUI interface. `store/` holds the state (chats, IDE, language servers, execution, updates, modules, Strata), `ui/` the views, and `web/` the WebView2 panes (`webview2-com`, no wry), the Office conversion and Markdown export.

- The carrier spawns `windows-host/rainy-host.exe` on Windows, `wsl.exe --distribution <d> --exec env … <runtime>/rainy-host` in WSL and `ssh.exe … -- <destination> …` for SSH (see below). The Host prints `RAINY_CONTROL {"type":"ready","protocol":1,"url":…}` on stdout and accepts `stop`, `inspect-activity` and `inspect-project` lines on stdin (`carrier/src/control.rs`, `host/src/control.rs`). The Host's own requests go the other way and the carrier answers each with a `reply` line: every Host asks `credential-key` once at start, the Windows Host asks `system-proxy {id, url}` for each origin it connects to, which the carrier resolves with WinHTTP's Windows proxy settings, bypass list and PAC scripts (`proxy.rs`), and Windows and WSL Hosts ask `preview` to drive the agent's hidden browser page.
- The carrier opens `ready.url` (`http://127.0.0.1:<port>/?token=…`) to get the Host's HttpOnly cookie; every later request and WebSocket upgrade carries it. The interface talks to the Host over `/rpc` (requests, replies, events) and to language servers over `/rainy/ide/lsp`.
- Documents the interface does not draw itself (PDF, Office, rich Markdown, media, the project map, the AI's built-in browser) are shown in WebView2 child windows that load `/?view=…` from the Host: `src/renderer/viewer/ViewerApp.tsx`. A page talks to the window through `window.ipc` (text changes, saves, links, outline position, exports) and the window calls `window.__rainyViewer`.
- Interface strings are in `native/crates/app/assets/messages.json` (Chinese and English per key); the Host writes its messages with `l(zh, en)` (`host/src/locale.rs`) in the language chosen in Settings → General.
- Settings → General → Diagnostics packs versions, the scrubbed end of the logs and the newest WebView2 crash dumps into a zip (`app/src/store/diagnostics.rs`). Nothing is uploaded.
- The installed app keeps its Explorer integration in `HKCU\Software\Classes` (`carrier/src/shell.rs`): the "Open with Rainy" verbs, a `Rainy.<extension>` ProgID per supported type with `OpenWithProgids`, and the `RegisteredApplications` capabilities Default apps reads. Both parts are off until the user turns them on (`explorerIntegration` in `desktop.json`). Removal deletes Rainy's own keys and values and a parent only when that left it empty and it was not among the keys that existed when the part was turned on (`explorerIntegration.keep`, read by the uninstaller too); the uninstaller runs `RainyAgent.exe --rainy-unregister-shell` and then deletes the keys itself. Paths on the command line, and those a second instance forwards to the first (`instance.rs`), are checked, mapped for WSL with `wslpath` and opened as projects or as files in their project (`app/src/launch.rs`).
- Markdown export renders the document to one self-contained HTML page in the viewer page (`src/renderer/ide/viewers/markdown-export.ts`); for PDF the window prints that page in a hidden WebView2 through the DevTools protocol and fixes the text of Kangxi radicals (`app/src/web/export.rs`, `pdf_text.rs`).

### Strata

The Strata engine is the optional module `strata` (about 560 MB: Niko1221/Strata, Python and the CUDA runtime). `carrier/src/strata/` manages it on Windows: the settings in the carrier's data folder, resolving the user's model (a main GGUF with its shards, the matching MTP weights, or a Strata profile) with 3.x's fingerprint cache, starting and stopping the engine process, and a loopback health check that never triggers a model load. The card in Settings → Models (`app/src/ui/settings/strata.rs`, state in `store/strata.rs`) shows the engine, the model and the server; it notices a Strata server another process started and never stops one it did not start. Connect and use by default sends the server's address to the current Host (`models.connectStrata`), which checks the loaded model and context itself (`host/src/strata.rs`) before saving the `rainy-strata` model. A WSL or SSH Host can only use it when it reaches that address; Rainy never switches to a cloud model instead.

### SSH targets

An execution target has the kind `windows`, `wsl` or `ssh` (`carrier/src/targets.rs`). SSH targets come from the aliases in `~/.ssh/config` and from the hosts added in Settings, which are saved as `sshHosts` in `desktop.json`; `RAINY_SSH_CONFIG` points at another config file for development and tests. Switching target restarts the app into the new target.

- `carrier/src/ssh.rs` validates destinations (`[user@]host` or an alias, never starting with `-`), builds the `ssh` arguments with `--` before the destination, and runs Python on the server through a `python3 -c` loader that receives the script and its arguments as base64, so any login shell (sh, bash, zsh, fish or csh) passes them unchanged. It also turns ssh failures into messages. The client is the Windows OpenSSH `C:\Windows\System32\OpenSSH\ssh.exe`, so the user's config, keys, ssh-agent and ProxyJump apply.
- `carrier/src/askpass.rs` answers ssh's prompts: ssh runs `RainyAgent.exe` itself as `SSH_ASKPASS`, which forwards the prompt to the running window; the host-key confirmation and the password, passphrase and one-time-code dialogs appear in the main window, and answers are kept in memory for the app run only.
- First, the carrier installs this version's Linux runtime in `~/.rainy-agent/runtime/` on the server with `scripts/install-runtime.py`: the base (the Linux IDE tools, identified by its content) once, and the application layer (`rainy-host`, the viewer pages and resources) per version. `--fetch` makes the server download the base pieces itself and verify each one; when that fails or stays below 256 KiB/s after a minute, the carrier sends the archive over ssh. Both check the archive against the SHA-256 pinned in the signed release resources. Runtimes of earlier versions are pruned in the background.
- The Host starts through ssh with `RAINY_PORT` set and `ssh -L` forwarding the same port from 127.0.0.1 on the PC to 127.0.0.1 on the server; the carrier checks that the Host reports the forwarded port. The Host home is `~/.rainy-agent` on the server, and it keeps its own carrier state, so projects and project memory stay on the server. API keys are sealed there under the key the carrier supplies at each start.

## Interface layouts

`app/src/ui/workbench.rs` draws the window in one of two layouts; `app/src/ui/agent/` holds what is particular to Agent mode.

- **Agent mode** (the default): the chat sidebar, the conversation and, on demand, a panel on the right with the files and the editor, the terminals or the chat's changes. **IDE mode**: the 4.2 workbench, with the file, search, Git, history and outline pane, the editor area with the bottom panel, and the AI pane. The title bar's two toggles, Ctrl+Shift+A and the command palette switch between them.
- Both layouts draw the same entities, which the `Workbench` owns: `ChatPane`, `HistoryPanel`, `FileTree`, `EditorArea`, `TerminalPanel` and the chat's `ChangesBar`. A switch only changes how they are drawn (`ChatPane::set_wide`, `HistoryPanel::set_sidebar`, `ChangesBar::set_docked`), so the selected chat, its draft, runs, open files and terminals carry over. Each entity is drawn in one place per frame: the changes are in the panel or above the composer, never both.
- `agent::fit` lays out the Agent columns for a window width: the conversation keeps 420 px while the window allows, an open panel takes the sidebar's place unless it keeps its width beside it, and a sidebar that does not fit is shown over the conversation on demand (Ctrl+B). The columns are resizable; the widths and the layout are kept per machine in `layout.json` in the user data folder (`placement.rs`), beside `window-state.json`, which keeps the 3.x shape.
- A file opened for the user (a tool card, a link in a reply, a change to review, quick open, or a new tab outside a project's restore) brings up the files panel (`agent::reveal_editor`). WebView2 pages show only where their area was painted (`web::end_frame`), so in Agent mode they appear only in the panel, and the sidebar shown over the conversation leaves the panel uncovered.
- An entity's asynchronous updates (`update_in`) go to the window that last drew it. The workbench reads the `Ide` every frame, so the projects load into this window before any view that shows them is drawn.
- Choosing a chat of another project in the sidebar shows that project, so its files, file links and new chats belong to it. A chat created for a message is selected only while the selection has not moved since the message was sent (`Store::selections`).

## Host

`host/src/main.rs` reads the environment (`env.rs`), creates the data directories and constructs these modules in order:

| Module | Owns |
|---|---|
| `server.rs` | The loopback HTTP server: launch-token auth, routes, the viewer pages, the `/rpc` WebSocket, the `/rainy/ide/lsp` WebSocket |
| `rpc.rs` | Method table and event broadcast; the types are `rainy-protocol` and `src/shared/rpc.ts` |
| `settings.rs`, `credentials.rs` | `settings.json` and the API keys under the Host home, in the 3.x formats |
| `network.rs` | The proxy for model requests and MCP servers: follow the system (default), none, or a manual HTTP proxy (reqwest). Loopback, private, `.local` and single-label hosts stay direct. Following the system, the Windows Host asks the carrier per origin (answers kept 30 seconds) and the WSL Host reads `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY`. Commands and terminals are not proxied |
| `agent/` | Models and model requests, chats, tools, system prompt, compaction, project memory, skills, MCP; `agent/service.rs` registers its RPC methods |
| `ide/` | File tree, editor state, run/debug, terminals, language servers, formatting, the `/rainy/ide/raw` byte route, change hints |
| `map/` | Project maps: the file list, line counts, imports, stack and the AI explanation |
| `search.rs` | Text search across a project's roots with ripgrep's walk and regex crates in process, and replacement on disk (`search.text`, `search.replace`) |
| `git.rs` | The Git pane: status, staging, discarding, committing and the AI commit message (`git.*`) |
| `runtime.rs`, `projects.rs`, `registry.rs` | Interpreter discovery and selection; projects and the project registry shared with the carrier |
| `pdfjs.rs` | Serves the pdf.js build in `resources/pdfjs` at `/rainy/pdfjs/` for the PDF viewer |

The Host is built with `panic = "abort"`: a panic ends the process and the window offers to restart it with the chat history kept. Code that may run on a plain thread (a terminal reader, a file watcher) spawns tasks through a runtime handle it captured, never `tokio::spawn`.

### Agent

- `agent/models.rs` stores model profiles, presets, discovery and the connection probe. `agent/llm/` speaks the three wire protocols Rainy uses — OpenAI Chat Completions (`completions.rs`), OpenAI Responses without server state (`responses.rs`) and Anthropic Messages with the hour-long prompt cache (`anthropic.rs`) — and streams each into one reply format, the one 3.x chats stored. Tool arguments are parsed as models write them, also cut short or with stray control characters (`llm/json.rs`). Requests to one model server are limited: one at a time for a loopback server, four otherwise.
- `agent/run.rs` is the agent loop: ask the model, run the tool calls of its reply, add the messages the user steered in, and ask again until the model answers without calling a tool. `agent/session.rs` holds one open chat: its transcript on disk (`agent/store.rs`), the loop while it runs, and the events the interface follows. Before each run the context is rebuilt from the transcript (`agent/context.rs`): a fresh system message followed by the compacted conversation. It records how long each thinking block streamed (`thinkingMs` on the assistant entry, by content index).
- The reply being streamed reaches the interface as `session.stream` at most every 50 ms: the whole message when it starts and every 2 seconds, and in between only a patch (`agent/stream.rs`) with the characters appended to text and reasoning blocks and any block that is new or changed otherwise. A patch names the length it continues from, so a client whose copy does not match skips patches until the next whole message; `sessions.get` moves the Host's baseline to the copy it returns. Until their arguments are complete, tool calls carry only the leading names (`file_path`, `command`, …) found in the first 4 KiB of the partial JSON.
- `agent/retry.rs` decides which failed requests a run retries by itself: overload, rate limits, dropped connections and timeouts, not authentication, quota or malformed requests. The request layer retries a failed request twice on its own first; a run then retries at most three times, after 5, 10 and 20 s with ±15% jitter or the delay the provider asks for (up to 2 minutes), and publishes the wait as `retry` in `session.state` so the interface can count down. `chat.retry` ends that wait early, or, when the chat is idle and its last model-visible entry is a failed or stopped reply, starts a run that answers the history as it stands. Each failed reply stays in the transcript; an `auto-retry` notice marks the retries.
- `agent/tools/` implements `read`, `grep` and `glob` (ripgrep's walk and regular expressions, in process), `write`, `edit` and `bash` (WSL, Linux) or `pwsh` (Windows). Tool arguments are checked against the tool's schema first (`tools/schema.rs`). Write and edit require a prior read of an existing file, and keep the replaced content under `snapshots/<sessionId>/` (`agent/snapshots.rs`, files up to 16 MiB) so the user can undo the change; an undo is refused when the file changed since, and a `context` entry with `reverted` tells the model. Large results are cut to a head and tail window, and the full text is saved under the Host temp directory. The file tools read UTF-8, UTF-16 with a byte-order mark and GB18030 (GBK) text (`tools/encoding.rs`); `read` names an encoding other than UTF-8, refuses binary files, and `edit` and `write` store a file in its own encoding only when its bytes convert back unchanged. On Windows, command output that is not UTF-8 is read in the locale's legacy code page (GBK on a Chinese system).
- A command started with `background: true` keeps running after its call: `tools/jobs.rs` keeps it per chat (at most 8, with 256 KiB of unread output each), `command_output` takes what it has written since the last read, and `stop_command` ends it. A chat stops its commands when it closes, and the interface lists them above the composer with a stop button.
- `task` runs a sub-agent (`agent/subagent.rs`): its own transcript and the chat's model, with `read`, `grep`, `glob` and `web_search` only, so no call of its own waits for the user. It stops after 24 assistant turns or 5 minutes, its usage counts toward the chat's run, and only its report reaches the chat. A step made of `task` calls alone runs them at the same time; any other step runs its calls in order.
- `web_search` and `web_fetch` use DeepSeek's Search and Fetch APIs with the user's DeepSeek key (`tools/web.rs`).
- `browser_open`, `browser_read`, `browser_act` and (for models that accept images) `browser_screenshot` show the agent the application it is building (`tools/browser.rs`). The page runs in a hidden WebView2 the window owns, with its own empty profile, every permission request refused and only loopback addresses opened; the Host reaches it through the `preview` control request, which the carrier offers to Windows and WSL Hosts but not to an SSH Host, whose localhost is not this machine's.
- The agent's changes are reviewed per chat (`agent/changes.rs`). `chat.changes` lists the files the chat's write and edit calls changed that are neither kept nor undone, counting lines against the text before the first change (Myers' diff; binary files and files over 4 MB are not compared) and leaving out a file changed back. `chat.changeBase` returns a file's text before the first change and now, `chat.keep` records reviewed calls as a `review` line in the chat file, and `session.changes` tells the interface to refresh. With `prefs.autoKeepChanges` (on by default) a user message that starts a run first keeps every pending change; a retry or a steering message does not.
- `agent/permissions.rs` decides every tool call by the chat's mode. `read-only` refuses changes, commands and MCP tools not marked `readOnlyHint`; `ask` (the default) runs reads and writes inside the project roots but waits for the user on commands, other MCP tools and writes outside the project (links resolved first); `auto` runs everything. A waiting call is answered with `chat.approve`. "Always allow" stores a command prefix or MCP tool per project in `settings.json`; prefixes match only commands without chaining, redirection, substitution, wrappers like `sudo` or inline code like `python -c`. A refusal without a reason ends the run after the current step; a new message refuses the waiting call and is steered to the model.
- `agent/prompt.rs` assembles the system prompt in a fixed order, so it stays byte-identical across the requests of a chat: persona, @-reference note, tool notes, MCP server instructions, extra project roots, skill descriptors, the user's global prompt and the working-directory line. `agent/instructions.rs` injects `AGENTS.md`/`CLAUDE.md` files as a user message before the first request of a session.
- `agent/compaction.rs` replaces an older span of the conversation with a summary when the request estimate (`agent/budget.rs`) reaches the budget threshold, after a context-overflow error, or on `/compact`. While the chat's previous request started less than 54 minutes ago with the same model and reasoning level, the summary request repeats exactly what the next request would send and appends one instruction, so it reads the prompt cache that request left. A reply that calls a tool, stops early, is empty or is far over the size limit is discarded; then, and when the cache is cold or the full history would not fit, a separate request summarizes only the span. The compaction entry records which request produced the summary and the usage of both.
- `agent/memory/` keeps per-project notes, generates them while the app is idle and recalls them once at the start of a session. Generation costs model requests, so it is off for projects without a memory record.
- `agent/inline.rs` serves the editor's AI. `inline.complete` streams a suggestion at the cursor (`prefs.completionModel`, or the chat model, with a 15 s limit), reporting the text so far as `inline.progress` events, so ghost text appears before the model has finished; a newer request ends the older one, and nothing is sent while `prefs.inlineCompletion` is off. `inline.edit` streams a rewrite of the marked selection with the chat model and stops on `inline.cancel`. Replies are cleaned to what fits: code fences, a repeated line start and, in the middle of a line, anything past one line or already after the cursor are dropped.
- `agent/skills.rs` lists `SKILL.md` files from `<cwd>/.rainy/skills` and `~/.rainy-agent/skills`. `agent/mcp/` connects the MCP servers configured in Settings over a program's standard streams, Streamable HTTP or the older HTTP+SSE transport (`mcp/client.rs`); a local server gets three minutes to start and list its tools, because one started through `uvx` or `npx` may download packages first. A bare command name resolves through `PATHEXT` on Windows, so `npx` starts `npx.cmd`. Each server's tools can be switched off one by one (`disabledTools`), which takes effect at the next message without reconnecting. Computer use is not built in: Settings → Skills & MCP fills in a server for [Windows-MCP](https://github.com/CursorTouch/Windows-MCP), pinned to one release with its dependencies resolved as published before a fixed date, its tools that duplicate Rainy's command, file and web tools excluded, and its telemetry off. A WSL Host starts it through `cmd.exe /c`; an SSH Host is not offered it, because the server would run on the remote machine.

### Editor backend

- `ide/files.rs` and `ide/fs.rs` serve the file tree and file operations with version checks: a version is `dev:ino:size:mtimeNs:ctimeNs`, the token 3.x stored, and every path is resolved again right before it is used. `ide/state.rs` keeps tabs, unsaved buffers, layout and run settings under `<home>/ide`, saved only over the revision the client last saw.
- `ide/hints.rs` watches the directories of files open in editor tabs (the `notify` crate, up to 64 per project folder) and run and debug events, and sends a throttled `ide.hint` event; the client then fetches the state with its usual requests. Watchers close when the client has not checked a folder's files for 30 seconds, because Windows cannot rename a watched folder.
- `ide/language.rs` runs one language server per editor connection over `/rainy/ide/lsp`: ty for Python, TypeScript 7's native `tsc --lsp` for JavaScript and TypeScript, and the installed clangd for C and C++ (`ide/tools.rs`). `ide/format.rs` formats unsaved text with Ruff for Python and TypeScript's own formatter for JavaScript and TypeScript.
- `ide/execution.rs` runs terminals, runs and launch-only debug sessions per project, with a bounded history of ordered events; programs run in a pseudo-terminal (`ide/pty.rs`, ConPTY on Windows). `ide/resolve.rs` turns a run configuration into explicit commands with every path inside the project and no shell interpreting arguments. `ide/debug.rs` and `ide/dap.rs` debug Python through debugpy, JavaScript and TypeScript through js-debug on the user's Node.js, and C and C++ through CodeLLDB on Windows and GDB's DAP interpreter on Linux. `ide/owner.rs` stops every process tree an operation started when it closes (`process.rs`).
- `ide/raw.rs` serves `/rainy/ide/raw`: the bytes of one project file for the viewers, with single ranges for media seeking and hex paging, and `Content-Security-Policy: sandbox`, so a file opened there runs no script.

### Project map

- `map/scan.rs` lists a project's files (`.gitignore` respected, hidden files included; at most 20,000 files, of which 8,000 and 96 MB are read, within 15 s), counts lines and marks vendored, generated and minified files so they do not count as code.
- `map/imports.rs` follows imports in JavaScript and TypeScript (with `tsconfig` paths), Python, C and C++, Go, Rust, Java and Kotlin, PHP, Ruby, Lua, shell, PowerShell, HTML and CSS. `map/stack.rs` names languages, frameworks and tools from manifests and imports.
- `map.get` keeps a scan for 20 seconds and runs one scan per project at a time. `map/graph.rs` (and `src/shared/map-graph.ts`, which the page draws with) turns the files into at most 16 boxes per view: a directory holding over 35% of the code is split, and the boxes are linked by their imports. `map.explain` asks the chat model for a summary and a sentence per part, and stores it under `maps/`.

### Search and Git

- `search.text` searches every root (`.gitignore` respected, hidden files included, `.git`, `node_modules`, `.venv` and `__pycache__` left out, files over 8 MB skipped) and returns at most 5000 matches with UTF-16 columns; patterns use JavaScript's syntax, and look-arounds are supported. A newer search of a project ends the older one. `search.replace` rewrites UTF-8 files on disk line by line, keeping a BOM and line endings.
- `git.rs` runs the `git` command with the runtime overlay, so the MinGit of the Windows basic component serves when Git is not installed. The status comes from `git status --porcelain=v2 -z --branch --untracked-files=all -- .` with paths made relative to the root. Discarding deletes untracked files with `git clean` and restores tracked ones from the index. `git.message` sends the staged diff (or every change when nothing is staged, cut to 24,000 characters) and the last twelve commit subjects to the chat model.

### Data under the Host home

The Host home is `RAINY_HOME`: `%APPDATA%\RainyAgent\native-home` for the Windows Host, `~/.rainy-agent` inside WSL and `~/.rainy-agent` on an SSH server. Every file is replaced atomically (`store.rs`), and the formats are those of 3.x, so 3.x, 4.0 and 4.1 read each other's data.

| Path | Content |
|---|---|
| `settings.json` | Models (without keys), selected model, global prompt, MCP servers (with their environment, request headers and switched-off tools), UI preferences, network proxy, default permission mode and remembered approvals |
| `.credentials.sealed.json` | API keys, each encrypted with AES-256-GCM and bound to its name, under a key the carrier keeps in `credential-key.bin` in its user data folder (`%APPDATA%\RainyAgent`), protected by Windows DPAPI (`carrier/src/credential.rs`) |
| `.credentials.json` | Version 1 key file, empty once its keys are sealed, so an older version starts without keys instead of failing. A Host started without the carrier keeps keys here as plain text |
| `chats/<sessionId>.jsonl` | One chat: a header line, then transcript entries in order |
| `chats/index.json` | Chat summaries for the history list; rebuilt from the files when missing |
| `maps/<workspaceId>.json` | The AI explanation of a project map |
| `snapshots/<sessionId>/` | Content replaced by the agent's write and edit calls, for undo; removed with the chat and after 30 days |
| `projects.json` | Projects (workspaces) and their roots |
| `ide/<workspaceId>.json` | Editor tabs, dirty buffers, layout and run configurations |
| `runtime-environments.json` | Interpreter selections per project |
| `<carrier-state>/project-memory/<projectId>/memory.v1.json` | Project memory, shared by the Windows and WSL Hosts; an SSH Host keeps its own under its home |

### Transcript entries

A chat file is JSON Lines; a line a crash left partial is skipped, and the next record written after it starts on a new line. The first line is `{"type":"header","version":1,…}`. Each later line is either `{"type":"entry","entry":…}` with one transcript entry (`user`, `assistant`, `toolResult`, `context`, `compaction`, `notice` or `turn`), `{"type":"meta",…}` with a title, model, archive or pin change, or `{"type":"review","kept":[…]}` with the tool calls whose changes the user kept. The model context is rebuilt from the entries: a `compaction` entry replaces the entries it covers with its summary, and `notice` and `turn` entries never reach the model.

## Viewer pages

`src/renderer` is the React code of the pages the window shows in WebView2 (`viewer/ViewerApp.tsx`). `rpc.ts` connects to `/rpc`.

- The window picks the viewer from the file type (`host/src/ide/preview.rs`, `app/src/ui/ide/viewers.rs`) and the tab's view (`source`, `preview`, `split` or `hex`), and loads the page with `?view=`. Images, audio, video and PDF bytes come from `/rainy/ide/raw`; the URL carries the observed version, so a changed file gets a new URL.
- PDF uses the pdf.js build the Host serves at `/rainy/pdfjs/`, with `isEvalSupported: false` (CVE-2024-4367). Word documents (`.docx`) are drawn by the page and spreadsheets as tables; slides and legacy Word documents are converted to PDF by the Microsoft Office or WPS Office installed on the computer, through the window's `__RAINY_OFFICE__` bridge (`app/src/web/office.rs`).
- Markdown is rendered with the chat renderer (`chat/Markdown.tsx`) relative to the document's directory, and edited in place by the rich view (`ide/viewers/RichMarkdown.tsx`); KaTeX and Mermaid load only when a document uses them. File previews and exports keep raw HTML through an allowlist and drop comments (`ide/viewers/markdown-html.ts`). In split view the page and the source editor follow each other's scrolling (`scrollToLine` in, `{ type: 'scroll' }` out).
- The rich view never writes the editor's whole serialization over a file: an edit is merged into the file's own text line by line, else block by block, and taken only when the merged text reads back as the document the editor holds (`ide/viewers/markdown-merge.ts`); untouched lines keep their spelling and line ends (CRLF files stay CRLF). Its code blocks use Crepe's own CodeMirror packages, resolved by `scripts/codemirror-alias.ts`.
- The rich view reads and writes the dialect the preview reads (`ide/viewers/rich-syntax.ts`): reference links and images keep their `[text][ref]` form while their target is the definition's, and definitions stay where they are as read-only blocks; `[TOC]` is a block that lists the headings and is written back as spelled; `==text==` is a highlight (Ctrl+Shift+H, toolbar). Text `$` is written without an escape wherever each top-level block, read again without it, gives the same document, so dollar amounts never become formulas. The preview and exports draw `[TOC]` as links to the heading ids (`rehypeToc` after `rehypeAnchors`).
- The project map draws the architecture graph (layered layout in `map/layout.ts`), file blocks (squarified treemap in `map/treemap.ts`) and the agent's activity from `session.tool` and streamed tool calls (`map/activity.ts`).
- Colors come from the tokens in `theme/` (`--rainy-*`), set from the interface's color scheme and accent.

## Build and packaging

- `pnpm run build` (`scripts/build.ts`) builds the viewer pages into `dist/renderer`, including `THIRD_PARTY_NOTICES.txt` with the license texts of every bundled npm package.
- `native/scripts/build-hosts.sh` builds `rainy-host.exe` and the Linux `rainy-host`; `native/scripts/build-release.sh` builds `RainyAgent.exe` with the release keys.
- `scripts/prepare-ide-tools.py` lays out the pinned IDE tools per platform (Ruff, ty, TypeScript 7's native compiler, debugpy, js-debug) from `toolpacks/ide-tools.sources.json`.
- `scripts/stage-windows.mjs` assembles the Windows Host runtime (`runtime/windows-host`: `rainy-host.exe`, the viewer pages and resources) and `scripts/stage-linux.py` the Linux runtime that WSL and SSH targets share, in two layers: the base `linux-runtime.tar.xz` (the Linux IDE tools, identified by its content, downloaded only when it changes) and the application layer `linux-app.tar.gz` (`rainy-host`, the viewer pages and resources), which ships in the installer. `install-runtime.py` unpacks both on the target (with the system's `xz` when Python lacks `lzma`). The offline Ubuntu 26.04 packages are the optional module `linux-dev-packages`, which the carrier downloads when the user installs the development tools.
- `scripts/package-native.mjs` stages `RainyAgent.exe` with the Host runtimes and `WebView2Loader.dll`, signs the resource inventory and packages the NSIS installer; `scripts/package.ps1` runs the whole release build.
