# Rainy architecture

Rainy is one Windows desktop application written in Rust: the interface, `RainyAgent.exe`, is drawn with GPUI, and the backend, `rainy-host`, runs where the user's files are. Since 4.1 no part of Rainy runs on Node.js. Documents the interface does not draw itself are React pages shown in WebView2. There is no plugin framework: every part is a plain module that `native/crates/app/src/main.rs`, `native/crates/host/src/main.rs` or `src/renderer/main.tsx` constructs explicitly.

## Processes

```text
RainyAgent.exe (native/crates/app + carrier)   window and interface (GPUI), updates, optional modules, Strata, WSL setup, SSH targets
  │  spawns over stdio (RAINY_CONTROL lines)
  ▼
rainy-host, one per execution target: rainy-host.exe on Windows, rainy-host inside a WSL distro or on a Linux server over SSH
  │  HTTP + WebSocket on 127.0.0.1:<random port>, launch-token cookie
  ▼
RainyAgent.exe connects to /rpc; WebView2 panes load the viewer pages (src/renderer/viewer) from the same origin
```

The Cargo workspace in `native/` has four crates:

- `rainy-protocol` (`crates/protocol`): the types of the `/rpc` protocol and the streaming patches, shared by the Host and the interface. `src/shared/rpc.ts` holds the TypeScript side the viewer pages use.
- `rainy-host` (`crates/host`): the Host, built for Windows and, with `cargo-zigbuild`, for x86_64 Linux with glibc 2.17 (`native/scripts/build-hosts.sh`).
- `rainy-carrier` (`crates/carrier`): what Electron main did in 3.x. It starts the Host for an execution target, answers its control requests, connects to `/rpc` and the language-server sockets, and owns the credential key (DPAPI), the system proxy lookup (WinHTTP), SSH (including recursive config `Include`, per-host profiles, askpass and standalone `-L` port forwarding in `ssh_tunnel.rs`), WSL setup, optional modules, Strata, signed resources, updates, single instance, the window state and the Explorer integration.
- `rainy` (`crates/app`, built as `Rainy.exe` and installed as `RainyAgent.exe`): the GPUI interface. `store/` holds the state (chats, IDE, language servers, execution, updates, modules, Strata), `ui/` the views, and `web/` the WebView2 panes (`webview2-com`, no wry), the Office conversion and Markdown export.

- The carrier spawns `windows-host/rainy-host.exe` on Windows, `wsl.exe --distribution <d> --exec env … <runtime>/rainy-host` in WSL and `ssh.exe … -- <destination> …` for SSH (see below). The Host prints `RAINY_CONTROL {"type":"ready","protocol":1,"url":…}` on stdout and accepts `stop`, `inspect-activity` and `inspect-project` lines on stdin (`carrier/src/control.rs`, `host/src/control.rs`). The Host's own requests go the other way and the carrier answers each with a `reply` line: every Host asks `credential-key` once at start, the Windows Host asks `system-proxy {id, url}` for each origin it connects to, which the carrier resolves with WinHTTP's Windows proxy settings, bypass list and PAC scripts (`proxy.rs`), and Windows and WSL Hosts ask `preview` to drive the agent's hidden browser page.
- The carrier opens `ready.url` (`http://127.0.0.1:<port>/?token=…`) to get the Host's HttpOnly cookie; every later request and WebSocket upgrade carries it. The interface talks to the Host over `/rpc` (requests, replies, events) and to language servers over `/rainy/ide/lsp`.
- Documents the interface does not draw itself (PDF, Office, rich Markdown, media, the project map, the AI's built-in browser) are shown in WebView2 child windows that load `/?view=…` from the Host: `src/renderer/viewer/ViewerApp.tsx`. Navigation is restricted to the exact Host origin and `about:blank`, and `window.ipc` is injected only on that exact Host origin (text changes, saves, links, outline position, exports); the window calls `window.__rainyViewer`.
- Interface strings are in `native/crates/app/assets/messages.json` (Chinese and English per key) plus native desktop/carrier strings in `native/crates/app/src/i18n.rs::NATIVE` and `native/crates/carrier/src/locale.rs::localized()`; the Host writes its messages with `l(zh, en)` (`host/src/locale.rs`) in the language chosen in Settings → General.
- Settings → General → Diagnostics packs versions, the scrubbed end of the logs and the newest WebView2 crash dumps into a zip (`app/src/store/diagnostics.rs`). Nothing is uploaded.
- The installed app keeps its Explorer integration in `HKCU\Software\Classes` (`carrier/src/shell.rs`): the "Open with Rainy" verbs, a `Rainy.<extension>` ProgID per supported type (75 text extensions; double-clickable script types `.bat`, `.cmd`, `.sh`, `.bash` and `.zsh` are never registered and are actively retired) with `OpenWithProgids`, and the `RegisteredApplications` capabilities Default apps reads. Both parts are off until the user turns them on (`explorerIntegration` in `desktop.json`). Startup checks all three context verbs and the full extension inventory so upgrades backfill newly added extensions and repair partial damage. Removal deletes Rainy's own keys and values and a parent only when that left it empty and it was not among the keys that existed when the part was turned on (`explorerIntegration.keep`, read by the uninstaller too); the uninstaller runs `RainyAgent.exe --rainy-unregister-shell` and cleans up any remaining HKCU entries in the original user's context after elevated per-machine uninstall. Paths on the command line, and those a second instance forwards to the first (`instance.rs`), are checked, mapped for WSL with `wslpath` and opened as projects or as files in their project (`app/src/launch.rs`).
- Markdown export renders the document to one self-contained HTML page with a script-disabling CSP `<meta>` in the viewer page (`src/renderer/ide/viewers/markdown-export.ts`); for PDF the window prints that page in a hidden WebView2 with scripts disabled (`SetIsScriptEnabled(false)`) through the DevTools protocol and fixes the text of Kangxi radicals (`app/src/web/export.rs`, `pdf_text.rs`).

### Strata

Strata is a tool the user downloads in Settings → Tools (`app/src/ui/settings/tools.rs`, the card in `ui/settings/strata.rs`, state in `store/strata.rs`); `carrier/src/strata/` manages it on Windows. `control.rs` reads the install manifest of Strata's newest GitHub release, downloads the Strata Terminal ("Control") zip, checks it against the manifest's SHA-256 and GitHub's asset digest, unpacks it (`carrier/src/unzip.rs`) and confirms it with `strata update --check --no-engine` (Strata's signed feed); `strata update` then installs the engine, and a newer Control that Strata installs itself is followed through `components/control/active.json`. `mcp.rs` talks to Strata's management server (`tools/strata_mcp.py`, the one Strata's app uses) for the model catalog with what fits this PC (`catalog.rs`), model downloads with progress and cancel, and removal. `process.rs` runs every Strata process with the folders of `env.rs`: `LOCALAPPDATA`, `APPDATA`, the install and components folders inside `<user data>\tools\strata`, a writable temporary folder with an ASCII path, no credential-like or outside Python variables, inside a Job object that ends them with Rainy. Models start through `strata launch` and stop with `launch --stop`; `health.rs` reads the server's status without loading a model. `Manager` in `mod.rs` keeps one job at a time, checks the feed after start and every six hours, and updates when no model runs. Connect and set as default sends the server's address to the current Host (`models.connectStrata`), which checks the loaded model and context itself (`host/src/strata.rs`) before saving the `rainy-strata` model. A WSL or SSH Host can only use it when it reaches that address; Rainy never switches to a cloud model instead.

### SSH targets

An execution target has the kind `windows`, `wsl` or `ssh` (`carrier/src/targets.rs`). SSH targets come from `~/.ssh/config` (including recursive `Include` directives) and from the hosts added in Settings (`sshHosts` in `desktop.json`); `RAINY_SSH_CONFIG` points at another config file for development and tests. Switching between Windows, WSL and SSH targets happens in place (`Store::swap_target_in_place` in `app/src/store/mod.rs`) without restarting `RainyAgent.exe`, and emits `StoreEvent::HostReconnected` once the new Host's session cookie is ready so IDE state, language servers, terminals, WebView2 viewers and remote panels rebind cleanly to the new origin.

- `carrier/src/ssh.rs` validates destinations (`[user@]host` or an alias, never starting with `-`), recursively parses `~/.ssh/config` and `Include` patterns (supporting relative `~/.ssh/`, `~/`, glob `*`/`?`, quoting, `#` comments, enclosing `Host` scope, cycle detection via active call stack, depth limit 8, file count limit 64 and canonical root containment against `..` or symlink traversal) into `SshHostSummary`, caches `ssh -G` `RemoteCommand` checks per target, builds `ssh` arguments with `--` before the destination (defaulting to `ServerAliveInterval=10` and `ServerAliveCountMax=3`), and runs Python on the server through a `python3 -c` base64 loader so any login shell passes arguments unchanged. The client is Windows OpenSSH (`C:\Windows\System32\OpenSSH\ssh.exe`), so the user's config, keys, ssh-agent and ProxyJump apply.
- Per-host research profiles are stored backward-compatibly in `desktop.json` under `sshHostProfiles` (`SshHostProfile` in `carrier/src/targets.rs`): custom persistent `RAINY_HOME` (e.g. an NFS volume inside an ephemeral container), default workspace, bookmarked directories (shown at the top of `app/src/ui/ide/folder_dialog.rs`), extra remote environment variables (`RAINY_SSH_EXTRA_ENV` JSON), keepalive overrides, saved `-L` port-forward presets and short host safety notes (`RAINY_SSH_NOTES`).
- `carrier/src/askpass.rs` answers ssh's prompts: ssh runs `RainyAgent.exe` itself as `SSH_ASKPASS`, which forwards prompts to the running window, keeping answers in memory for the run only. When an SSH Host connection drops, the interface enters a non-blocking exponential-backoff auto-reconnect (`1s → 3s → 8s` in `app/src/store/mod.rs` and `ui/ssh.rs`), stopping immediately on authentication refusal and restoring active `-L` tunnels on recovery.
- First, the carrier probes `<RAINY_HOME>/runtime/` (default `~/.rainy-agent/runtime/`, overridden via `install-runtime.py --home` or `RAINY_HOME`) with zero archive upload (`install-runtime.py --probe`, reading and writing files in explicit UTF-8): when this version is already installed, the Host starts immediately without uploading `linux-app.tar.gz` and earlier runtimes can be pruned on the same connection. Only when missing does the carrier stream `linux-app.tar.gz` over stdin; `--fetch` lets the server download and verify base pieces itself, falling back to `--receive` upload over ssh when that fails or stays below 256 KiB/s after a minute. Background `--prune` uses non-interactive `BatchMode=yes`.
- The Host starts through ssh with `RAINY_PORT` set and `ssh -L` forwarding the same port from 127.0.0.1 on the PC to 127.0.0.1 on the server; the carrier checks the reported port, tracks the remote Host PID for `/proc`-verified `BatchMode=yes` force-stop if graceful shutdown times out, and forwards `RAINY_HOME`, `RAINY_SSH_NOTES` and `RAINY_SSH_EXTRA_ENV` through the launcher payload. API keys are sealed under the remote Host home using the key the carrier supplies at each start.
- Dynamic user port forwarding (`carrier/src/ssh_tunnel.rs`, `app/src/ui/tunnels.rs`) runs one lightweight standalone `ssh -N -T -o ExitOnForwardFailure=yes -L 127.0.0.1:<local>:<remoteHost>:<remote> -- <dest>` child per active rule set, preflight-checking local port conflicts and cleaning up its process tree on rule change or exit without interrupting the primary Host connection. Combined with `host.ports` listening-port discovery, users can forward and open TensorBoard, Jupyter or web services in one click.
- On remote targets, the status bar renders a compact resource pill (`app/src/ui/metrics.rs`) that polls `host.metrics` every 5 seconds only while the window is active, showing GPU count/memory, real cgroup CPU/memory limits (rather than host `nproc`) and disk free space, with an on-demand popover (`includeGpuProcesses: true`) listing per-GPU bars, process owners/PIDs, bookmarked disk paths and host notes.

## Interface layouts

`app/src/ui/workbench.rs` draws the window in one of two layouts; `app/src/ui/agent/` holds what is particular to Agent mode.

The optical look (`optics` in the interface preferences, Settings → Appearance) lives in `app/src/ui/optics/`: `look.rs` derives its colors from the theme and caps the glow and the glass by contrast (body text at least 7:1, muted text and level names at least 4.5:1 at the worst place they can sit); `backdrop.rs` paints the field of characters behind a new chat glyph by glyph from hashes of place and time, at most 10 frames a second and only while the window is active, the page is shown, the pointer moved over it in the last 45 s and Windows' animation effects are on; `pet.rs`, `slider.rs` and `usage.rs` are the pixel pet on the composer (its pose is a pure function of the page's clock), the reasoning slider of the model card and the usage overview. The overview reads `usage.stats` (`host/src/agent/usage.rs`), which counts the chat files incrementally, as searches read them.

- **Agent mode** (the default): the chat sidebar, the conversation and, on demand, a panel on the left by default (matching IDE mode's files, editor, chat order; `panel_left: true` in `app/src/placement.rs`, movable to the right and remembered) with the files and the editor, the terminals or the chat's changes. **IDE mode**: the classic workbench, with the file, search, Git, history and outline pane, the editor area with the bottom panel, and the AI pane. The title bar's two toggles, Ctrl+Shift+A and the command palette switch between them.
- Both layouts draw the same entities, which the `Workbench` owns: `ChatPane`, `HistoryPanel`, `FileTree`, `EditorArea`, `TerminalPanel` and the chat's `ChangesBar`. A switch only changes how they are drawn (`ChatPane::set_wide`, `HistoryPanel::set_sidebar`, `ChangesBar::set_docked`), so the selected chat, its draft, runs, open files and terminals carry over. Each entity is drawn in one place per frame: the changes are in the panel or above the composer, never both.
- `agent::fit` lays out the Agent columns for a window width: the conversation keeps 420 px while the window allows, an open panel takes the sidebar's place unless it keeps its width beside it, and a sidebar that does not fit is shown over the conversation on demand (Ctrl+B). The columns are resizable; the widths and the layout are kept per machine in `layout.json` in the user data folder (`placement.rs`), beside `window-state.json`, which keeps the 3.x shape.
- A file opened for the user (a tool card, a link in a reply, a change to review, quick open, or a new tab outside a project's restore) brings up the files panel (`agent::reveal_editor`). WebView2 pages show only where their area was painted (`web::end_frame`), so in Agent mode they appear only in the panel, and the sidebar shown over the conversation leaves the panel uncovered.
- An entity's asynchronous updates (`update_in`) go to the window that last drew it. The workbench reads the `Ide` every frame, so the projects load into this window before any view that shows them is drawn.
- Choosing a chat of another project in the sidebar shows that project, so its files, file links and new chats belong to it. A chat created for a message is selected only while the selection has not moved since the message was sent (`Store::selections`).

## Host

`host/src/main.rs` reads the environment (`env.rs`), creates the data directories and constructs these modules in order:

| Module | Owns |
|---|---|
| `server.rs` | The loopback HTTP server: launch-token auth, routes, the viewer pages, the `/rpc` WebSocket, the `/rainy/ide/lsp` WebSocket |
| `rpc.rs` | Method table and event broadcast; the types are `rainy-protocol` and `src/shared/rpc.ts` |
| `settings.rs`, `credentials.rs` | `settings.json` and the API keys under the Host home, in the 3.x formats |
| `network.rs` | The proxy for model requests and MCP servers: follow the system (default), none, or a manual HTTP proxy (reqwest). Loopback, private, `.local` and single-label hosts stay direct. Following the system, the Windows Host asks the carrier per origin (answers kept 30 seconds) and the WSL Host reads `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY`. Commands and terminals are not proxied |
| `agent/` | Models and model requests, per-model profiles (`profile.rs`), orchestration (`orchestrate.rs`), prompts (`prompts.rs`), hooks (`hooks.rs`), `@` completion (`complete.rs`), chats, tools, permissions, prompt, compaction, project memory, skills, MCP, and external CLI agents & quota (`agent/external/`); `agent/service.rs` registers its RPC methods |
| `ide/` | File tree, editor state, large-log `files.tail`, run/debug, terminals, language servers, formatting, `/rainy/ide/raw` byte downloads and `/rainy/ide/upload` streaming uploads, change hints |
| `sysinfo.rs` | Host resource metrics (`host.metrics`: cgroup v1/v2 CPU & memory limits, `/proc`, `nvidia-smi` GPU & on-demand process owners, disk usage), listening port discovery (`host.ports`) and cached static SSH prompt context |
| `experiments.rs` | Detached long-running experiment manager (`experiments.{list,start,stop,remove,tail}`), persisted under `$RAINY_HOME/experiments.v1.json` outside Host process ownership so training jobs survive SSH disconnects and Host restarts |
| `map/` | Project maps: the file list, line counts, imports, stack and the AI explanation |
| `search.rs` | Text search across a project's roots with ripgrep's walk and regex crates in process, and replacement on disk (`search.text`, `search.replace`) |
| `git.rs` | The Git pane: status, staging, discarding, committing and the AI commit message (`git.*`) |
| `runtime.rs`, `projects.rs`, `registry.rs` | Interpreter discovery (including `/opt/conda`, `mambaforge`, `~/.venvs`, `uv`, and read-only CUDA metadata probing without creating CUDA contexts or allocating VRAM) and selection; projects and the project registry shared with the carrier |
| `pdfjs.rs` | Serves the pdf.js build in `resources/pdfjs` at `/rainy/pdfjs/` for the PDF viewer |

The Host is built with `panic = "abort"`: a panic ends the process and the window offers to restart it with the chat history kept. Code that may run on a plain thread (a terminal reader, a file watcher) spawns tasks through a runtime handle it captured, never `tokio::spawn`.

### Agent

- `agent/models.rs` stores model profiles, presets, discovery and the connection probe. `agent/llm/` speaks the three wire protocols Rainy uses — OpenAI Chat Completions (`completions.rs`), OpenAI Responses without server state (`responses.rs`) and Anthropic Messages with the hour-long prompt cache (`anthropic.rs`) — and streams each into one reply format, the one 3.x chats stored. Chats and sub-agents on Anthropic's own API use message threads (`llm/thread.rs`, beta `message-threads-2026-08-12`): the first request starts a thread with the whole conversation, and each later one sends only the messages after the previous reply with that reply's id, as long as the earlier messages, the fixed fields (model, thinking, effort, tools, system prompt, betas) and the five minutes Anthropic keeps a thread still hold; otherwise, or when the thread is not found, the whole conversation starts a new one, and a conversation Anthropic refuses a thread for goes on with whole requests. Messages carry no breakpoints on a thread; a top-level `cache_control` caches each request's end. `RAINY_CLAUDE_THREADS=0` turns threads off. Side requests (summaries, titles, the editor's AI) never use one. Tool arguments are parsed as models write them, also cut short or with stray control characters (`llm/json.rs`). Requests to one model server are limited: one at a time for a loopback server, four otherwise.
- `agent/run.rs` is the agent loop: ask the model, run the tool calls of its reply, add the messages the user steered in, and ask again until the model answers without calling a tool. `agent/session.rs` holds one open chat: its transcript on disk (`agent/store.rs`), the loop while it runs, and the events the interface follows. Before each run the context is rebuilt from the transcript (`agent/context.rs`): a fresh system message followed by the compacted conversation. It records how long each thinking block streamed (`thinkingMs` on the assistant entry, by content index).
- The reply being streamed reaches the interface as `session.stream` at most every 50 ms: the whole message when it starts and every 2 seconds, and in between only a patch (`agent/stream.rs`) with the characters appended to text and reasoning blocks and any block that is new or changed otherwise. A patch names the length it continues from, so a client whose copy does not match skips patches until the next whole message; `sessions.get` moves the Host's baseline to the copy it returns. Until their arguments are complete, tool calls carry only the leading names (`file_path`, `command`, …) found in the first 4 KiB of the partial JSON.
- `agent/retry.rs` decides which failed requests a run retries by itself: overload, rate limits, dropped connections and timeouts, not authentication, quota or malformed requests. The request layer retries a failed request twice on its own first; a run then retries at most three times, after 5, 10 and 20 s with ±15% jitter or the delay the provider asks for (up to 2 minutes), and publishes the wait as `retry` in `session.state` so the interface can count down. `chat.retry` ends that wait early, or, when the chat is idle and its last model-visible entry is a failed or stopped reply, starts a run that answers the history as it stands. Each failed reply stays in the transcript; an `auto-retry` notice marks the retries.
- `agent/tools/` implements `read`, `grep` and `glob` (ripgrep's walk and regular expressions, in process), `write`, `edit`, `apply_patch` (all updates and deletes verify prior read via `Observations`), `bash` (WSL, Linux) or `pwsh` (Windows), and read-only IDE/map bridge tools (`lsp_diagnostics`, `symbol_outline`, `module_deps`). After `edit`, `write` or `apply_patch`, any new Error-level diagnostics from the Host's shared LSP pool are appended automatically when a language server is available. Tool arguments are checked against the tool's schema first (`tools/schema.rs`). Write and edit require a prior read of an existing file, and keep the replaced content under `snapshots/<sessionId>/` (`agent/snapshots.rs`, files up to 16 MiB) so the user can undo the change (including Hunk-level accept/revert in the Diff view); an undo is refused when the file changed since, and a `context` entry with `reverted` tells the model. Large results (including MCP tool results) are cut to a head and tail window, and the full text is saved under the Host temp directory. The file tools read UTF-8, UTF-16 with a byte-order mark and GB18030 (GBK) text (`tools/encoding.rs`); `read` names an encoding other than UTF-8, refuses binary files, and `edit` and `write` store a file in its own encoding only when its bytes convert back unchanged. On Windows, command output that is not UTF-8 is read in the locale's legacy code page (GBK on a Chinese system).
- A command started with `background: true` keeps running after its call: `tools/jobs.rs` keeps it per chat (at most 8, with 256 KiB of unread output each), `command_output` takes what it has written since the last read, and `stop_command` ends it. A chat stops its commands when it closes, and the interface lists them above the composer with a stop button.
- `task` runs a sub-agent (`agent/subagent.rs`): its own transcript and the chat's model (or an optional model override), with `read`, `grep`, `glob`, `web_search` and read-only code navigation tools so no call of its own waits for the user. It stops after 24 assistant turns or 5 minutes, its usage counts toward the chat's run, and only its report reaches the chat. A step made of `task` calls alone runs them at the same time; any other step runs its calls in order. Multi-agent `swarm` sessions support optional per-worker model overrides, budget/turn circuit breakers, non-preemptive message delivery that preserves pending approvals, and three-way worktree handoff (`git apply -3`).
- `web_search` and `web_fetch` use DeepSeek's Search and Fetch APIs with the user's DeepSeek key (`tools/web.rs`).
- `browser_open`, `browser_read`, `browser_act` and (for models that accept images) `browser_screenshot` show the agent the application it is building (`tools/browser.rs`). The page runs in a hidden WebView2 the window owns, with its own empty profile, every permission request refused and only loopback addresses opened; the Host reaches it through the `preview` control request, which the carrier offers to Windows and WSL Hosts but not to an SSH Host, whose localhost is not this machine's.
- The agent's changes are reviewed per chat (`agent/changes.rs`). `chat.changes` lists the files the chat's write and edit calls changed that are neither kept nor undone, counting lines against the text before the first change (Myers' diff; binary files and files over 4 MB are not compared) and leaving out a file changed back. `chat.changeBase` returns a file's text before the first change and now, `chat.keep` records reviewed calls as a `review` line in the chat file, and `session.changes` tells the interface to refresh. With `prefs.autoKeepChanges` (on by default) a user message that starts a run first keeps every pending change; a retry or a steering message does not.
- `agent/permissions.rs` decides every tool call by the chat's mode, wildcard allow rules (`git diff *`), and highest-priority `deny` rules (commands, paths and tools) stored in `settings.json`. `read-only` refuses changes, commands and MCP tools not marked `readOnlyHint`; `ask` (the default) runs reads and writes inside the project roots but waits for the user on commands, other MCP tools, out-of-workspace reads/grep/glob, out-of-workspace `shell.workdir`, and writes outside the project (links resolved first); `auto` runs everything not explicitly denied. Command tokenization strips quotes and skips leading options (e.g. `git -C`) before matching rules. Declarative lifecycle hooks (`PreToolUse` exit-code-2 blocking, `PostToolUse`/`PostEdit`, `Stop`) run from user settings and trusted workspaces (`.rainy/hooks.json`). A waiting call is answered with `chat.approve`. A refusal without a reason ends the run after the current step; a new message refuses the waiting call and is steered to the model.
- `agent/prompt.rs` assembles the system prompt in a fixed order, so it stays byte-identical across the requests of a chat: persona, @-reference note, tool notes, XML-delimited untrusted MCP server instructions and skill descriptors, extra project roots, the user's global prompt and the working-directory line (on SSH targets, appending a `OnceLock`-cached static summary of real cgroup CPU/memory limits, GPU topology with a 2 s probe timeout, and sanitized `RAINY_SSH_NOTES`). `agent/instructions.rs` injects `AGENTS.md`/`CLAUDE.md` files as a user message before the first request of a session (project instructions and `.rainy/skills` load in every workspace and are fenced as untrusted data; only `.rainy/hooks.json`, which runs commands, waits for workspace trust).
- `agent/external/` integrates external CLI coding agents over their official documented stdio JSON-RPC 2.0 protocols (`external/jsonrpc.rs` with `ProcessJob`/`CREATE_NO_WINDOW` and Unix process-group cleanup, stripping internal `RAINY_*` secrets while preserving user CLI auth): `external/codex.rs` drives `codex app-server --stdio` (mapping Rainy's `read-only`/`ask`/`auto` modes to Codex sandbox and approval policies, streaming text/reasoning/tool items/diffs and bidirectional approvals), and `external/acp.rs` implements the Agent Client Protocol (`agy acp` for Antigravity plus user-configured ACP commands). Under Antigravity personal OAuth, `acp.rs` passes through natively as the primary agent (`fs: false, terminal: false`) without injecting Rainy's system prompt, built-in tools, `/swarm` or `orchestrate`. Rainy's own `/swarm` never runs in an external chat: ACP agents get every `/command` as typed (Antigravity's `/swarm` and `/teamwork` start its own swarm and teamwork), the commands an agent lists (`available_commands_update`, read from the moment the session is made but never a `session/load` replay) go to the interface as `external.commands` and into `ExternalAgentStatus.commands`, and Codex, which has no `/swarm`, is told to ask for sub-agents in words. `external/team.rs` shows the team an external agent runs (`external.team`, `external.teamMember`, `external.teamChanged`): Antigravity's is read from its own folders (`~/.gemini/antigravity{,-cli}/brain/<conversation>/.system_generated`: `subagents/*.json` give the tree of members and teamwork roles, `swarm/members.json`, `plan.json` and `board.jsonl` the swarm, `logs/transcript.jsonl` each member's latest steps), followed by the chat every 1.5 s while anyone works and 5 s otherwise (a new conversation's folder appears only once Antigravity works in it, so it is looked for every 1.5 s while the chat runs); Codex's comes from its notifications (`subAgentActivity`, `collabAgentToolCall`, the sub-agents' own threads), each sub-agent is a card in the chat with its answer, and an approval a sub-agent asks for names it (`PendingApproval.agent`) and is answered on its thread. The swarm pane (`ui/agent/swarm.rs`) shows that team read-only: board, members with their state, focus, checklist and steps, and the plan. `ExternalManager` (`external/mod.rs`) pools processes lazily with idle reclamation and exposes `external.{status,probe,configure}` plus `external.changed`; external chats persist optional `externalBackend` and `externalThreadId` fields in `chats/<id>.jsonl` and `index.json` (and `externalAgents` in `settings.json`, backward-compatible with 3.x/4.x), reuse streaming patches, approvals and `ChangesBar` review (`undoable: false`), and are surfaced in `app/src/ui/chat.rs`, `ui/history.rs` and `ui/settings/external_agents.rs`.
- `agent/budget.rs` estimates what the next request costs: within a run, the input and output tokens the provider reported for the previous request plus a local estimate of the messages added since; otherwise the local estimate of the whole request, scaled by recent reported-to-estimated ratios (up or down, isolated per model). `session.contextBreakdown` exposes the per-segment breakdown (System, Instructions, MCP Tools, Core Tools, History, Recall) to the interface's context meter. The local estimate counts text, prices an image by its pixel size read from the file header (about 750 pixels a token, the long edge fitted to 2048) instead of its base64 text, and leaves out signatures and replay data.
- `agent/compaction.rs` frees context when the expected tokens reach the budget threshold or after a context-overflow error. First it clears old tool outputs, oldest first and never those of the latest step, down to half the threshold: a `cleared` entry names them, and the model reads a placeholder with the entry number and first line instead. When clearing cannot bring the chat well below the threshold, it compacts an older span, which `/compact` also does. The `contextStrategy` preference picks how: `recall` by default (also for 4.6's `auto`), or `summary`. `summary` asks the model for a checkpoint. While the chat's previous request started less than 54 minutes ago with the same model and reasoning level, the summary request repeats exactly what the next request would send and appends one instruction, so it reads the prompt cache that request left. A reply that calls a tool, stops early, is empty or is far over the size limit is discarded; then, and when the cache is cold or the full history would not fit, a separate request summarizes only the span. `recall` makes no request: `agent/history.rs` builds an index of the span (the user's messages, the latest plan, files changed and read, commands, errors, the last assistant message) with entry numbers. The compaction entry records which way the checkpoint was made (`mode`: `shared`, `separate` or `recall`) and the usage.
- `recall` (`agent/tools/recall.rs`) reads the chat's own entries back verbatim, by search or by entry number (from 1, in file order), so nothing cleared or compacted is lost to the model. It runs in every permission mode; sub-agents do not have it.
- `agent/memory/` keeps per-project notes, generates them while the app is idle and recalls them once at the start of a session. Generation costs model requests, so it is off for projects without a memory record.
- `agent/inline.rs` serves the editor's AI. `inline.complete` streams a suggestion at the cursor (`prefs.completionModel`, or the chat model, with a 15 s limit), reporting the text so far as `inline.progress` events, so ghost text appears before the model has finished; a newer request ends the older one, and nothing is sent while `prefs.inlineCompletion` is off. `inline.edit` streams a rewrite of the marked selection with the chat model and stops on `inline.cancel`. Replies are cleaned to what fits: code fences, a repeated line start and, in the middle of a line, anything past one line or already after the cursor are dropped.
- `agent/profile.rs` adapts the system prompt, edit tool and plan tool per model family (Claude, GPT/Codex, Gemini and open-weight models tuned for Claude Code) while keeping prompt prefixes stable for caching. `agent/orchestrate.rs` splits a single turn across a planner model and an executor model (`hand_off` / `replan`, handing back automatically after three consecutive tool errors) on one shared transcript.
- `agent/prompts.rs` (`prompts.*` RPC, surfaced in `app/src/ui/settings/prompts.rs`) exposes and overrides the three built-in prompt groups in `settings.json` (`builtinPrompts`), edits the global prompt and lists/edits global and per-project `AGENTS.md`/`CLAUDE.md` files. `agent/hooks.rs` runs declarative lifecycle hooks (`PreToolUse`, `PostToolUse`, `PostEdit`, `Stop`) from user `settings.json` (`hooks`) and trusted workspaces' `.rainy/hooks.json`. `agent/complete.rs` serves `@` completion over cached workspace file trees and chat history.
- `agent/external/quota.rs` (`external.quota`, rendered in `app/src/ui/quota.rs` and the usage overview Limits tab) reads Codex five-hour/weekly rate limits and Antigravity per-model-group quotas without starting a chat.
- `agent/skills.rs` lists `SKILL.md` files from `<cwd>/.rainy/skills` and `~/.rainy-agent/skills`. `agent/mcp/` connects the MCP servers configured in Settings over a program's standard streams, Streamable HTTP or the older HTTP+SSE transport (`mcp/client.rs`); a local server gets three minutes to start and list its tools, because one started through `uvx` or `npx` may download packages first. A bare command name resolves through `PATHEXT` on Windows, so `npx` starts `npx.cmd`. Each server's tools can be switched off one by one (`disabledTools`), which takes effect at the next message without reconnecting. Computer use is not built in: Settings → Skills & MCP fills in a server for [Windows-MCP](https://github.com/CursorTouch/Windows-MCP), pinned to one release with its dependencies resolved as published before a fixed date, its tools that duplicate Rainy's command, file and web tools excluded, and its telemetry off. A WSL Host starts it through `cmd.exe /c`; an SSH Host is not offered it, because the server would run on the remote machine.

### Editor backend

- `ide/files.rs` and `ide/fs.rs` serve the file tree and file operations with version checks: a version is `dev:ino:size:mtimeNs:ctimeNs`, the token 3.x stored, and every path is resolved again right before it is used. `files.tail` streams incremental tail chunks for large (>5 MiB) log files in `app/src/ui/ide/editor_area.rs`. `ide/state.rs` keeps tabs, unsaved buffers, layout and run settings under `<home>/ide`, saved only over the revision the client last saw.
- `ide/hints.rs` watches the directories of files open in editor tabs (the `notify` crate, up to 64 per project folder) and run and debug events, and sends a throttled `ide.hint` event; the client then fetches the state with its usual requests. Watchers close when the client has not checked a folder's files for 30 seconds, because Windows cannot rename a watched folder.
- `ide/language.rs` runs language servers over `/rainy/ide/lsp` and shares a lightweight `(workspaceId, rootId, language)` diagnostic pool (idle-reclaimed, awaited on close) with the agent: ty for Python, TypeScript 7's native `tsc --lsp` for JavaScript and TypeScript, and the installed clangd for C and C++ (`ide/tools.rs`). `ide/format.rs` formats unsaved text with Ruff for Python and TypeScript's own formatter for JavaScript and TypeScript.
- `ide/execution.rs` runs terminals, runs and launch-only debug sessions per project, with per-workspace bounded event histories and explicit `truncated` reporting; programs run in a pseudo-terminal (`ide/pty.rs`, ConPTY on Windows with OEMCP/GBK fallback and Windows Job Object `KILL_ON_JOB_CLOSE` containment; Unix shells preserve user rc/profile for bash/zsh/fish and inject `RAINY_SSH_EXTRA_ENV`). `ide/resolve.rs` turns a run configuration into explicit commands with every path inside the project and no shell interpreting arguments. `ide/debug.rs` and `ide/dap.rs` debug Python through debugpy, JavaScript and TypeScript through js-debug on the user's Node.js, and C and C++ through CodeLLDB on Windows and GDB's DAP interpreter on Linux. `ide/owner.rs` stops every process tree an operation started when it closes (`process.rs`). Detached training jobs (`experiments.rs`, surfaced in `app/src/ui/ide/experiments.rs`) intentionally run outside `Owner` via `setsid` (Unix) or detached process groups (Windows), verifying process start timestamps and UIDs/PGIDs before stopping to prevent PID reuse or killing another user's container process.
- `ide/raw.rs` serves `/rainy/ide/raw` (file bytes for viewers and streaming downloads, with single ranges and `Content-Security-Policy: sandbox`) and `POST /rainy/ide/upload` (authenticated, same-origin, 256 KiB chunked streaming upload up to 512 MiB with double workspace `realpath` containment, symlink-overwrite rejection and atomic rename, paired with `file_tree.rs` upload/download actions). Converted Office PDFs are streamed through one-time authenticated tokens on `/rainy/ide/office-pdf` (registered locally via `ide.registerOfficePdf` or uploaded via `POST /rainy/ide/office-pdf` for WSL/SSH) without Base64 round-trips.

### Project map

- `map/scan.rs` lists a project's files (`.gitignore` respected, hidden files included; at most 20,000 files, of which 8,000 and 96 MB are read, within 15 s), counts lines and marks vendored, generated and minified files so they do not count as code.
- `map/imports.rs` follows imports in JavaScript and TypeScript (with `tsconfig` paths), Python, C and C++, Go, Rust, Java and Kotlin, PHP, Ruby, Lua, shell, PowerShell, HTML and CSS. `map/stack.rs` names languages, frameworks and tools from manifests and imports.
- `map.get` keeps a scan for 20 seconds and runs one scan per project at a time. `map/graph.rs` (and `src/shared/map-graph.ts`, which the page draws with) turns the files into at most 16 boxes per view: a directory holding over 35% of the code is split, and the boxes are linked by their imports. `map.explain` asks the chat model for a summary and a sentence per part, and stores it under `maps/`.

### Search and Git

- `search.text` searches every root (`.gitignore` respected, hidden files included, `.git`, `node_modules`, `.venv` and `__pycache__` left out, files over 8 MB skipped) and returns at most 5000 matches with UTF-16 columns; patterns use JavaScript's syntax, and look-arounds are supported. A newer search of a project ends the older one. `search.replace` rewrites UTF-8 files on disk line by line, keeping a BOM and line endings.
- `git.rs` runs the `git` command with the runtime overlay, so the MinGit of the Windows basic component serves when Git is not installed. The status comes from `git status --porcelain=v2 -z --branch --untracked-files=all -- .` with paths made relative to the root. Discarding deletes untracked files with `git clean` and restores tracked ones from the index. `git.message` sends the staged diff (or every change when nothing is staged, cut to 24,000 characters) and the last twelve commit subjects to the chat model.

### Data under the Host home

The Host home is `RAINY_HOME`: `%APPDATA%\RainyAgent\native-home` for the Windows Host, `~/.rainy-agent` inside WSL and `~/.rainy-agent` (or the per-host `rainyHome` override in `sshHostProfiles`) on an SSH server. Every file is replaced atomically (`store.rs`), and the formats remain backward-compatible with 3.x so 3.x, 4.x and 5.0 read each other's data.

| Path | Content |
|---|---|
| `settings.json` | Models (without keys), selected model, external CLI agent configurations (`externalAgents`), built-in prompt overrides (`builtinPrompts`), global prompt, user lifecycle hooks (`hooks`), MCP servers (with their environment, request headers and switched-off tools), UI preferences, network proxy, default permission mode, trusted workspaces and remembered allow/deny rules |
| `external-models.json` | Cached model lists and supported reasoning levels discovered from external CLI agents (`codex`, `agy`, ACP), kept across restarts so the composer offers them before re-probing; while none are known, Codex's `model/list` and `agy models` fill it without opening a conversation (`agent/external/mod.rs`) |
| `.credentials.sealed.json` | API keys, each encrypted with AES-256-GCM and bound to its name, under a key the carrier keeps in `credential-key.bin` in its user data folder (`%APPDATA%\RainyAgent`), protected by Windows DPAPI (`carrier/src/credential.rs`); a damaged `Local State`, or one whose key DPAPI reports as invalid for the account, is backed up and rebuilt under DPAPI with an explicit warning; any other DPAPI failure changes nothing and the run keeps new keys in the private `.credentials.json` until a later run seals them |
| `.credentials.json` | Version 1 key file, empty once its keys are sealed, so an older version starts without keys instead of failing. A Host started without the carrier keeps keys here as plain text |
| `chats/<sessionId>.jsonl` | One chat: a header line, then transcript entries in order |
| `chats/index.json` | Chat summaries for the history list; rebuilt from the files when missing |
| `maps/<workspaceId>.json` | The AI's tour of a project (summary, how to run it, files to read first, key flows, where to make changes, a line per part) and the files it was written for |
| `snapshots/<sessionId>/` | Content replaced by the agent's write and edit calls, for undo; removed with the chat and after 30 days |
| `projects.json` | Projects (workspaces) and their roots |
| `ide/<workspaceId>.json` | Editor tabs, dirty buffers, layout and run configurations |
| `runtime-environments.json` | Interpreter selections per project |
| `experiments.v1.json` | Detached background experiment registry (PID, process start ticks/UID, log path and exit state) persisted across SSH disconnects |
| `<carrier-state>/project-memory/<projectId>/memory.v1.json` | Project memory, shared by the Windows and WSL Hosts; an SSH Host keeps its own under its home |

### Transcript entries

A chat file is JSON Lines; a line a crash left partial is skipped, and the next record written after it starts on a new line. The first line is `{"type":"header","version":1,…}`. Each later line is either `{"type":"entry","entry":…}` with one transcript entry (`user`, `assistant`, `toolResult`, `context`, `compaction`, `cleared`, `notice` or `turn`), `{"type":"meta",…}` with a title, model, archive or pin change, or `{"type":"review","kept":[…]}` with the tool calls whose changes the user kept. The model context is rebuilt from the entries: a `compaction` entry replaces the entries it covers with its summary or index, a `cleared` entry puts placeholders in place of the tool outputs it names, and `notice` and `turn` entries never reach the model. Versions before 4.6 skip `cleared` entries (they count them as damaged lines) and so see those outputs again.

## Viewer pages

`src/renderer` is the React code of the pages the window shows in WebView2 (`viewer/ViewerApp.tsx`). `rpc.ts` connects to `/rpc`.

- The window picks the viewer from the file type (`host/src/ide/preview.rs`, `app/src/ui/ide/viewers.rs`) and the tab's view (`source`, `preview`, `split` or `hex`), and loads the page with `?view=`. Images, audio, video and PDF bytes come from `/rainy/ide/raw`; the URL carries the observed version, so a changed file gets a new URL.
- PDF uses the pdf.js build the Host serves at `/rainy/pdfjs/`, with `isEvalSupported: false` (CVE-2024-4367). Word documents (`.docx`) are drawn by the page and spreadsheets as tables; slides and legacy Word documents are converted to PDF by the Microsoft Office or WPS Office installed on the computer, through the window's `__RAINY_OFFICE__` bridge (`app/src/web/office.rs`).
- Markdown is rendered with the chat renderer (`chat/Markdown.tsx`) relative to the document's directory, and edited in place by the rich view (`ide/viewers/RichMarkdown.tsx`); KaTeX and Mermaid load only when a document uses them. File previews and exports keep raw HTML through an allowlist and drop comments (`ide/viewers/markdown-html.ts`). In split view the page and the source editor follow each other's scrolling (`scrollToLine` in, `{ type: 'scroll' }` out).
- The rich view never writes the editor's whole serialization over a file: an edit is merged into the file's own text line by line, else block by block, and taken only when the merged text reads back as the document the editor holds (`ide/viewers/markdown-merge.ts`); untouched lines keep their spelling and line ends (CRLF files stay CRLF). Its code blocks use Crepe's own CodeMirror packages, resolved by `scripts/codemirror-alias.ts`.
- The rich view reads and writes the dialect the preview reads (`ide/viewers/rich-syntax.ts`): reference links and images keep their `[text][ref]` form while their target is the definition's, and definitions stay where they are as read-only blocks; `[TOC]` is a block that lists the headings and is written back as spelled; `==text==` is a highlight (Ctrl+Shift+H, toolbar). Text `$` is written without an escape wherever each top-level block, read again without it, gives the same document, so dollar amounts never become formulas. The preview and exports draw `[TOC]` as links to the heading ids (`rehypeToc` after `rehypeAnchors`).
- The project map shows the tour (`map/Tour.tsx`; the Host writes it in `host/src/map/tour.rs`, from the README, contributor notes, build files and the declarations of the central files, and keeps only paths and lines that exist), the AI footprint (`map/Footprint.tsx`, from `map.footprint`, which reads the chat's transcript in `host/src/map/footprint.rs`), and the structure: the architecture graph (layered layout in `map/layout.ts`), file blocks (squarified treemap in `map/treemap.ts`) and the agent's activity from `session.tool` and streamed tool calls (`map/activity.ts`). The side pane's file relations (`app/src/ui/ide/relations.rs`) read `map.relations` for the file in the editor.
- Colors come from the tokens in `theme/` (`--rainy-*`), set from the interface's color scheme and accent.

## Build and packaging

- `pnpm run build` (`scripts/build.ts`) builds the viewer pages into `dist/renderer`, including `THIRD_PARTY_NOTICES.txt` with the license texts of every bundled npm package.
- `native/scripts/build-hosts.sh` builds `rainy-host.exe` and the Linux `rainy-host`; `native/scripts/build-release.sh` builds `RainyAgent.exe` with the release keys.
- `scripts/prepare-ide-tools.py` lays out the pinned IDE tools per platform (Ruff, ty, TypeScript 7's native compiler, debugpy, js-debug) from `toolpacks/ide-tools.sources.json`.
- `scripts/stage-windows.mjs` assembles the Windows Host runtime (`runtime/windows-host`: `rainy-host.exe`, the viewer pages and resources) and `scripts/stage-linux.py` the Linux runtime that WSL and SSH targets share, in two layers: the base `linux-runtime.tar.xz` (the Linux IDE tools, identified by its content, downloaded only when it changes) and the application layer `linux-app.tar.gz` (`rainy-host`, the viewer pages and resources), the downloaded module `linux-app`, fetched only when a WSL distribution or SSH server lacks this version; the installer ships neither. `install-runtime.py` unpacks both on the target (with the system's `xz` when Python lacks `lzma`). The offline Ubuntu 26.04 packages are the optional module `linux-dev-packages`, which the carrier downloads when the user installs the development tools.
- `scripts/package-native.mjs` stages `RainyAgent.exe` with the Host runtimes and `WebView2Loader.dll`, signs the resource inventory and packages the NSIS installer; `scripts/package.ps1` runs the whole release build.
