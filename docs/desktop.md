# RainyAgent desktop

English | [中文](desktop.zh.md)

RainyAgent is a Windows x64 Electron carrier whose core installer includes the Windows Host. The Strata engine, Windows PHP and the WSL Linux runtime are optional components, and native tools are downloaded per tool. Model weights remain user-supplied. It preserves the upstream Agent loop, session persistence and Web chat with four default tools: `read`, `write`, `edit`, and the selected platform shell (`pwsh` or `bash`). The upstream baseline is version 0.1.7-rc.2.

The [Chinese installation and configuration guide](desktop-setup.zh-CN.md) owns the product workflow, configuration reference and source build instructions. [Validation](validation.md) distinguishes simulated providers from real API runs and records unresolved acceptance items. [Attribution](../THIRD_PARTY_NOTICES.md) describes the upstream and packaged dependencies.

## Offline installation and recovery

The [1.0.10 release](https://github.com/RainyMarks/RainyAgent/releases/tag/v1.0.10) provides the core installer. The [1.0.10 resource archive](https://github.com/RainyMarks/RainyAgent/releases/tag/v1.0.10-resources) holds the PHP component and the WSL runtime pieces; the [1.0.6 resource archive](https://github.com/RainyMarks/RainyAgent/releases/tag/v1.0.6-resources) holds the native-tool archives. The [1.0.0 resource archive](https://github.com/RainyMarks/RainyAgent/releases/tag/v1.0.0-resources) still holds the Strata archive, the `environment/` WSL installation media and the `environment-components/` runtime archives. The core starts natively on Windows without WSL or scientific libraries. Source packaging restores the pinned inputs of [the input manifest](../toolpacks/build-inputs.v1.json) under `release/offline-2.0.0`. Native tools are optional: the catalog downloads them per tool, and for offline installation every `rainy-unit-*.tar.gz` archive placed beside the setup EXE makes the installer install every unit. Without these archives, the installer keeps the existing tools.

The tool installation window reports the current stage, file and stage progress. Cancel requests a safe stop and waits for any required rollback. Re-running the installer with the same archives rechecks them and can reuse verified staging files. Corrupt archives and insufficient space stop installation before tool replacement. Before updating, save your work and close RainyAgent, native tools and their command windows; the installer reports occupied tools instead of terminating them.

Third-party Electron ASAR archives are installed, verified and backed up as complete binary files. Catalog probes and offline HTTP responses read these payloads through the unmodified disk filesystem. The carrier's own packaged pages retain normal ASAR loading and integrity protection. [The real Electron fixture](../tests/manual/toolpack-electron.mjs) checks installation, cancellation, retry, user-file preservation, catalog inspection and raw archive serving in a private temporary directory.

Upgrades preserve declared settings and user-added files in retained tool directories. A saved inventory for each installed package distinguishes program files from user files; obsolete program files are removed. An installation moves replaced or removed tool directories into `.rainy-toolpack/backups/<transactionId>/`. After the installation commits, backup files whose path, size and SHA-256 match a saved package inventory are deleted, so only user files and changed files remain for manual recovery. About 60 seconds after startup, the application applies the same cleanup to backups left by earlier versions; an unfinished switch or rollback keeps every backup. Directories outside the previous inventory remain untouched. A conflicting user path or missing prior inventory stops the upgrade before replacement and identifies the affected path. Recovery records, package inventories and the remaining backups stay under `.rainy-toolpack`. Uninstalling the application preserves `tools/`, `runtime/`, recovery records and user data.

New installations start on Windows; existing saved WSL choices are retained. Runtime settings list registered WSL2 distributions and can prepare an application-owned Ubuntu 26.04.1 environment from the external offline media. Creating WSL system components remains an explicit action, with administrator approval and a restart when Windows requires it. Existing distributions and their data are preserved. A missing saved distribution opens recovery instead of silently choosing another target. Clean-Windows administrator approval and restart recovery remain separate acceptance items.

## Optional components

The core installer does not contain the Strata engine, Windows PHP or the WSL Linux runtime archive (`linux-runtime.tar.gz`). The signed carrier resource `optional-modules.json` pins each component's archive, and the application downloads it on demand from GitHub release pieces into `%APPDATA%\RainyAgent\modules\<id>`. Each piece and the assembled archive are checked by SHA-256, interrupted downloads resume with HTTP Range requests, and cancellation keeps the downloaded pieces for the next attempt.

Settings → Runtime environments → Optional components downloads and removes the Strata engine (about 560 MB) and PHP. The Strata engine is the archive already published as the 1.0.0 build input `build-inputs/strata-runtime.tar.gz`; [Strata local inference](#strata-local-inference) describes its contents and use. PHP serves native Windows targets; Code workspace describes how a project selects it.

The WSL runtime (about 340 MB) is specific to each RainyAgent version and is published in the 1.0.10 resource archive. The first WSL launch after installing or updating downloads it, with progress on the startup page; if this version's runtime is already unpacked in the distribution, nothing is downloaded. If the download fails, the dialog offers Retry, continue with Windows native, or Exit. Continuing with Windows native records Windows as the execution target, like a switch in settings. About a minute after a WSL start, the installed application deletes the runtimes earlier versions unpacked in `~/.rainy-agent/runtime`, keeping this version's runtime and any runtime a running process still uses.

About 60 seconds after startup, the packaged application deletes resources that earlier installers left in its `resources` directory: `strata-runtime`, `php`, `linux-runtime.tar.gz`, `native-tools-metadata.json`, `native-tools-download.json` and `native-tools-catalog.json`.

## Application updates

The packaged app checks stable releases from `RainyMarks/RainyAgent` on GitHub at startup and downloads an available core update in the background. Help → Check for updates provides manual status and retry. A prepared update offers Later or Restart and install; installation starts only after confirmation, draft saving, and Host cleanup. A failed save keeps the app open. Ordinary exit does not install a downloaded update, and the updater does not select prereleases or downgrade the installed version.

Automatic updates replace the core application and preserve installed tools and environments. They do not download native tools, WSL media, or CPU/CUDA environment components again; the first WSL launch after an update downloads that version's WSL runtime. CPU/CUDA environment components are still imported from matching offline release files. [Validation](validation.md) records the update checks completed for the published artifacts.

## Runtime contract

The Host ([architecture](architecture.md)) has no official accounts, telemetry, office runtimes, browser/computer control, schedules, multi-agent tools or plugin marketplace. One selected Windows or WSL Host owns commands, terminals, model connections and sessions. The Windows carrier owns the window, native tool windows and shared project catalog. Lifecycle control uses stdin/stdout; authenticated HTTP/WebSocket carries application data. Target switching saves drafts and refuses running or queued Agent work, programs, debugging and terminals. New execution is frozen before the target preference changes.

WSL startup waits for Windows-side loopback TCP reachability after the Host reports readiness. Connection refusal is retried within the original 90-second startup deadline; other connection errors fail startup. This check sends no HTTP request or authentication token. Cancellation, timeout and Host exit stop probing, and transport shutdown waits for the owned socket and child process to close. Native Windows startup has no cross-OS probe.

The window appears at once on a startup page that reports each preparation step. It reopens at the size, position and maximized state saved when it last closed; a first launch, or a saved position whose display is disconnected, centers the default size on the primary display and maximizes it when that display is smaller. A WSL target recorded by an earlier launch skips the environment check window: startup maps the carrier paths in one WSL call and unpacks the Host, and opens the check only when that target is unavailable. Each launch appends its phase timings to `host.log`.

Native window controls share the single top toolbar. Empty header space supports dragging and double-click maximization; editing and zoom shortcuts remain available. Unified settings separate models, context, project memory, skills, MCP and runtime controls. Runtime settings select the execution target, inspect existing interpreters, import release-approved offline components and download optional components.

New workspaces show files on the left and the main editor. Top-toolbar buttons reveal AI conversations and the bottom panel when needed; View → Focus editor hides both. Existing workspaces retain their saved pane visibility and widths. File actions occupy one row, editor actions share the open-tab row, and CTF tools open as a closable tab. Tight windows can show files over the editor. Editor tabs, conversations and the retained CTF workbench keep separate state. The homepage and About credit read `Develop by NCUCyberBase`. Active reasoning displays “Thinking...” in English and “思考中” in Chinese; the elapsed-time control uses the corresponding localized text.

## Code workspace

A project starts from the folder explicitly opened by the user; a fresh installation does not create a desktop project. Add Folder attaches another root with its own stable identity, and cross-root file operations remain scoped by that identity. Windows projects use native paths; WSL projects use paths mapped and canonicalized inside the selected distribution. Existing workspaces retain their identity, editor recovery and source-target chats. Switching a project binds its public identity to the destination, restores directory mounts and selects that workspace before the Host is ready, while old chats and editor recovery remain in their original Host.

The CodeMirror 6 editor provides multiple file tabs, syntax highlighting loaded per file type, search and replacement, go to line, undo, explicit saves and inline differences. File operations preserve UTF-8 BOM and line endings. Binary, non-UTF-8 and over-limit documents are read-only; the default editable limit is 5 MiB. Oversized UTF-8 previews retain up to 64 KiB without splitting a character; binary previews show up to 4 KiB as hexadecimal. Quick Open searches workspace paths with a bounded result list and reports truncation. Changing the query, switching projects, or reopening Quick Open invalidates earlier results; pending or failed searches cannot open an old result.

Language services receive Host file URIs. The editor matches the URI spellings servers return, such as an encoded drive colon or a different letter case on Windows, to the same file, including Windows drive roots and UNC shares.

Recovery storage keeps dirty buffers, open tabs and pane geometry under each workspace. An external edit refreshes a clean buffer; a dirty buffer retains its text and offers a comparison. Version conflicts stop saving until the user resolves the displayed difference. Run and debug save every changed file in the current workspace and stop when a save fails.

Persistent language servers analyze unsaved editor documents: Pyright for Python, TypeScript Language Server for JavaScript/TypeScript, and clangd for C/C++. Completion, hover, signature help, diagnostics, go to definition (F12), references (Shift+F12) and rename (F2) come from these servers; rename also edits files that are not open, which then appear as unsaved tabs. Formatting uses the bundled Ruff and Prettier, or the prepared clang-format. Python interpreter choices and CMake compilation databases also configure editor language services. Selected code is sent through a normal recorded user message containing its path, range and text.

The run button runs the open file with the language its extension implies. The menu beside it chooses another language for that file, which the workspace remembers, or pins a saved configuration for another entry program; saving the open file's configuration does not pin it. Run configurations retain the entry, arguments, interpreter or compiler, working directory and CMake choices per workspace. Python supports files, modules and existing virtual environments; JavaScript and TypeScript use Node; PHP supports direct script runs; C/C++ supports single-file and CMake builds. Failed builds stop launch. Debugging uses debugpy, js-debug, CodeLLDB on Windows and GDB DAP on Linux for workspace-launched programs. The interface exposes breakpoints, stepping, stacks, variables, watches and stop. External process attachment and PHP debugging are unavailable.

Runtime discovery inspects project virtual environments, Conda registrations, common Python locations, PATH and imported components without installing packages into them. A selected interpreter configures project tools, terminals, runs and language services through a process-local environment. Executable readiness and library capabilities are reported separately; a working Python can lack PyTorch or CUDA. Interpreters from the other execution platform are rejected. Settings → Runtime environments → Optional components downloads PHP 8.5 with the json, openssl, mbstring, pdo_sqlite, curl and zip extensions for native Windows targets. Until it is downloaded, running a PHP file on a native Windows target reports where to download it; the run configuration can instead select an installed `php.exe`. An installed environment component or a project's selected PHP takes precedence. A WSL target uses the distribution's PHP.

Offline components provide isolated Python 3.12, Node 24, Windows PHP, native C/C++ tools, and separate CPU or CUDA scientific environments. Scientific components include NumPy, SciPy, pandas, scikit-learn, image processing, Jupyter and common deep-learning libraries, with matched PyTorch 2.11, torchvision 0.26 and torchaudio 2.11. Import verifies the release catalog, archive and file inventory before selecting a content-addressed generation. Existing user environments and global PATH are unchanged. CUDA needs a compatible NVIDIA driver. The Ubuntu 26.04 amd64 development wizard installs its verified C/C++, GDB, CMake, clangd and PHP packages with downloads disabled.

## CTF workbench

A private `native-tools.local.json` in the application user-data directory can override catalog entries with an existing local installation. Its version-1 object contains an absolute `root` and a version-1 `catalog` with the same tool-entry fields as the bundled catalog; entries use installation-relative paths under `tools/<id>/`. Matching IDs replace downloaded entries and other IDs extend the catalog. Local installations remain selected across tool updates and have no publisher functional-verification badge. For IDA Pro, point the local catalog at an officially installed program and activate your own license separately; neither its installer nor license belongs in the public tool channel.

Each tool directory, each shared runtime (Java 21, .NET 8) and the catalog file is an installation unit with its own `rainy-unit-<20 hex>.tar.gz` archive. The name derives from the unit's file inventory, so an unchanged tool keeps its archive across releases and is not downloaded again. Version 1.0.6 publishes 41 archives totalling about 2.1 GB; the largest, IDA, is about 383 MB, and small tools such as 7-Zip are about 1 MB. Tools that the offline installer placed in the application directory before 1.0.6 are updated in place there; otherwise tools live in `%APPDATA%\RainyAgent\native-tools`.

The tool channel uses signed format 2: `toolpacks/native-tools-channel.v2.signed.json`, with signature domain `RainyAgent/tool-channel/v2`, and the download source `toolpacks/native-tools-source.v2.json`. RainyAgent 2.x fetches newer revisions of this file from the `main` branch. `apps/rainy-desktop/toolpacks/` keeps the files at the locations that installed 1.x clients fetch: a byte-identical copy of `native-tools-channel.v2.signed.json` for 1.0.6 and later, and the version-1 `native-tools-channel.signed.json` for 1.0.5 and earlier. `build-tool-channel.mjs` and `sign-tool-channel.mjs` rewrite that copy whenever their output is `toolpacks/native-tools-channel.v2.signed.json`. The installer ships the channel as `resources/native-tools-channel.signed.json`; the application uses the higher revision of the shipped and the cached channel and ignores an older publisher revision. It rejects invalid signatures and mismatched catalogs, and does not accept new trust keys from the channel. Publishers package the staged tools, then build and sign the channel with a higher `--revision`:

```sh
node scripts/package-native-tools.mjs --stage <stage> --output <dir> [--previous <earlier metadata.json>]
node scripts/build-tool-channel.mjs --metadata <dir>/native-tools-metadata.json --archives <dir> --catalog <stage>/tools/manifest.json --version <x.y.z> --revision <n> --pieces <pieces dir> --source-output toolpacks/native-tools-source.v2.json --output toolpacks/native-tools-channel.v2.signed.json [--previous-source <earlier source>] [--key <publisher key>]
```

Upload the printed pieces to the `v<version>-resources` release and commit both toolpacks files and the 1.x copy. Archives listed in the previous source keep their earlier release location. Use the tool publisher identity matching `resources/native-tools-public-keys.json`; application rebuilds can retain those public keys without owning the tool signing key.

Common tools summarizes how many tools are downloaded. The card of a tool that is not downloaded shows Download with the tool's size instead of Open; a downloaded tool shows Open and Remove, which asks for a second click to confirm. An Update available tag marks outdated tools. The top buttons Download all (size) and Update downloaded tools (size) sit beside Check tool updates. Every transport piece and archive is checked by SHA-256 before installation; downloads support cancellation, Range resume and retry. Downloading a tool also installs the runtimes it needs and brings the other downloaded tools to the same catalog revision, downloading only changed units. Remove deletes the tool and any runtime that no remaining tool uses, without network access. Installed tools remain available offline across restarts and application updates. First visiting the catalog checks the signed tool channel; Check tool updates repeats the check.

The CTF entry works before a conversation is selected. Its default Common tools tab lists tools under task groups, searches names and uses, filters by group or by Downloaded, and shows favorites, recent launch requests, versions and availability. Favorites and recent entries belong to the Windows user and are shared across conversations. Saved Burp favorites migrate to Yakit; old Burp recent-launch entries are removed without recording a Yakit launch. The success message says “Launch request sent for {name}”; it confirms platform acceptance of the request. File availability, interface readiness and functional acceptance are separate observations. `status: ready` means required files and dependencies exist; the separate `verified` flag reflects recorded acceptance for the matching catalog. Unverified tools stay labeled Not verified, and missing dependencies disable launch. The directory does not add Agent tools or prompts.

Yakit 1.4.8-0919 includes the official Yak engine 1.4.8-beta19 in `bins/yak.zip` for its built-in engine restoration. The package requires no separate engine download. Yakit follows its configured `YAKIT_HOME`; its Windows default is `yakit-projects` beside `Yakit.exe`. The package retains Yakit's [AGPLv3 license](https://github.com/yaklang/yakit/blob/v1.4.8-0919/LICENSE.md) and upstream notices. ImHex remains available in Reverse for binary editing.

IDA carries private Python 3.12.14, matching SIP bindings and the `imp` compatibility module. RainyAgent starts it with a private `IDAUSR` directory under application data and removes inherited Python and Qt overrides. The shared Java 21.0.12.1 runtime starts StegSolve and JADX; dnSpy 6.6.0 carries .NET Desktop 10.0.9. The native-tool launcher searches packaged binaries and Windows system utilities, not a third-party system PATH. Windows still supplies its normal operating-system DLLs and device drivers.

The Windows multimon-ng build reads 16-bit mono raw audio. Its own directory includes SoX for other formats. From a directory containing `sample.wav`, run `sox.exe -R -t wav sample.wav -esigned-integer -b 16 -r 22050 -t raw sample.raw`, then `multimon-ng.exe -a DTMF -t raw sample.raw`. The tool card opens a terminal with its help text; it does not start microphone capture.

Cards with missing files offer Repair, which downloads again only the units whose files are missing or differ by SHA-256.

The IceSky tab opens the pinned browser workbench. One retained iframe provides its existing 22 manual tools, with templates and tool components loaded on first selection. Switching back to the directory keeps that iframe. Each conversation has an independent draft; opening IceSky without a conversation or from a blank New Session page uses a separate standalone draft. The workbench follows the application's theme and font sizes. Navigation and status controls follow the application language; bundled tool prose retains its original language.

The selected Host's durable storage retains editable text, options, text results and file metadata. Drafts do not restore file contents or generated binary artifacts; after a restart, select local files again when the restored draft requests them. Drafts exclude API credentials. AI requests use a bounded, authenticated relay to the endpoint configured inside IceSky, including localhost in the selected target; the relay does not persist request keys or bodies.

Text transformations, decoding and tokenization run in cancellable workers. Automatic calculation waits 160 ms after input changes and accepts at most 64 KiB of UTF-8 input; larger inputs require the Calculate button. Token results render 100 items per page. Tool loading, computation and draft-save failures keep the current draft available for retry or export. Conversation changes, workbench refresh, native menu or keyboard reload and application exit wait for pending draft saves; a failed reload or exit save keeps the window open.

## Strata local inference

The Strata engine is an optional component of about 560 MB containing Niko1221/Strata 0.1.39, Python 3.12.14, and the required server, preparation, and CUDA runtime dependencies. When the engine is missing, Models → Strata local model shows a Download button; Runtime environments → Optional components also lists it. Users do not need a separate Strata or Python installation. The inference engine targets Windows x64 and NVIDIA CUDA 13 with driver 580 or newer; the supplied engine includes `sm75`, `sm86`, `sm89`, and `sm120` targets. This package provides no AMD or Linux inference engine. The [runtime source manifest](../toolpacks/strata-runtime.sources.json) pins its inputs and licenses.

Users supply a supported Qwen3.8 Flash Next main GGUF with all shards, plus its matching MTP GGUF or prepared MTP directory. No main/MTP weights or derived dense/expert files are distributed with the runtime. In Models → Strata local model, choose the main source, MTP source or compatible profile, then save. An empty MTP path asks the manager to detect matching files beside the main model; API serving still requires MTP. An explicit Start prepares required model files locally before loading the server, without downloading weights. Preparation and startup can be cancelled.

The card controls the engine context window, loopback port, KV cache, reserved VRAM and resident RAM budget. Settings are stored privately under the carrier's application data directory, at `strata/settings.json`; selected model files remain outside the install directory. Only processes started by this manager can be stopped. An existing external server is identified separately and is not terminated by the card. Request reasoning and output limits remain in the ordinary model configuration.

Connect and use by default asks the selected Host to verify the actual loaded model and context before saving the local endpoint. Strata runs on Windows even when the project Host is WSL. If WSL NAT prevents access to Windows loopback, select the Windows execution target for Strata; the application does not rewrite network settings or substitute a cloud model.

Current Strata validation covers relocation of the engine runtime, Python imports, and health/chat integration with a mock server. It does not yet establish real GPU inference, throughput, or compatibility across hardware. [Validation](validation.md) owns the tested artifact and remaining acceptance items.

## Model experience

Each request is estimated before it is sent: system prompt, tool declarations and messages. The composer's context meter shows that estimate, or the usage the provider reported for the last request. When the estimate reaches the compaction threshold, an older span of the chat is replaced by a summary. The span never includes the latest user request and never separates a tool call from its result. The summary directive asks for verified progress, exact paths, errors, unresolved work and the next action, and forbids restating user goals or constraints. A context-overflow error compacts and retries once; `/compact` compacts on request. A failed summary leaves the history unchanged. Explicit output limits, including the DeepSeek preset's maximum, take precedence over defaults.

Requests to one endpoint origin share a queue in arrival order. A loopback server (Base URL host localhost, `*.localhost`, 127.0.0.1 or [::1]) runs one request at a time; any other endpoint runs up to four, so parallel chats and background requests do not wait for each other's complete streams. A stream that sends nothing for five minutes is aborted, and one request may run for at most 30 minutes.

Settings → Models → Global prompt saves instructions, at most 4,000 characters, that every chat's system prompt includes, including chats already open. Compaction summaries, project memory and connection probes keep their own prompts; an empty prompt adds nothing.

Model settings live in the selected Host's `settings.json`; API keys live in its `.credentials.json` (mode 0600), and an environment variable with the same name takes precedence. New API models default to OpenAI Responses and local models to Chat Completions; the defaults remain editable to match the service. The DeepSeek preset uses 1,000,000 context tokens. Both Claude presets share the Anthropic key, offer only the reasoning levels the model accepts, and keep the prompt cache for an hour. Model discovery requires only a provider, Base URL, protocol and optional request key; it saves nothing. Saving and the separate streaming/tool-call check require the complete model configuration. RainyAgent never silently substitutes another model. On first start, models, keys and the global prompt of a 1.x profile are imported once; 1.x chats are not.

Skills are folders with a `SKILL.md` under `<project>/.rainy/skills` and `~/.rainy-agent/skills`. Only their names and descriptions, at most 4,096 tokens together, enter the system prompt; the model reads a skill's file when it needs it. MCP servers are configured once in Settings → Skills & MCP and serve every chat over stdio or streamable HTTP. Their tools appear as `mcp__<server>__<tool>`, calls time out after 60 seconds, and server instructions join the system prompt. The IDA preset launches the IDA MCP server through `uvx`.

Tools run without approval prompts. The read tool pages lines, by default 2,000 lines, 2,000 characters per line and 50 KiB; its long-line marker is explicit and the file stays intact. Write and edit require a prior read of an existing file and keep its BOM and dominant line ending. Shell commands (`bash` on WSL, `pwsh` on Windows) time out after 60 seconds by default and 10 minutes at most; long output keeps its head and tail in the reply and the full text in a file under the Host temp directory. Workspace instructions (`AGENTS.md`, `CLAUDE.md` and their `.local` variants, at most 64 KiB) enter a chat once before its first request, and instructions of subdirectories the agent works in are added when it reaches them. Chat titles use the first user message.

## Project memory

Project memory uses the carrier project identity across execution targets. Windows and WSL share the project record; environment-specific notes retain their target scope. Use and automatic generation have independent switches. Human edits require the displayed revision, and generated updates cannot replace or remove a manually corrected note. Deletion retains source watermarks and exclusion hashes so old evidence does not recreate a removed note.

After a completed turn, generation waits for 60 seconds without foreground work and runs at most once per project every 10 minutes. It uses the selected model with no tools, at most 4,096 input tokens and 512 output tokens, a 30-second timeout, and no automatic cloud fallback. New foreground input cancels the auxiliary request. At most 1,024 estimated tokens of active notes are stored; new chats receive at most 512 tokens and 5% of their input budget, including recall framing. Failed, cancelled or stale-revision generation preserves the prior record. Recall enters the chat as a context entry marked as historical data, so later requests replay it from the chat file. Source file changes invalidate dependent generated facts; original session logs remain available.

## Usage license and release integrity

[RainyAgent source-available terms](../LICENSE) permit personal and internal business use without a license fee, modification, and noncommercial redistribution; sale, paid hosting, and commercial redistribution require separate written permission. Startup and execution do not read device codes, activation codes or expiry dates, and settings contains no activation controls. Existing activation files remain in place and do not affect startup or execution. Projects, model settings and chats retain their existing storage locations.

The production carrier authenticates its resource inventory using a public release key embedded at build time and retains Electron ASAR integrity protection. Build keys are independent of user data: the default lives in the ignored build directory, or RAINY_RELEASE_SIGNING_KEY selects an existing Ed25519 private-key file; private keys never enter the distribution. Windows Authenticode signing uses a separately configured certificate.

The first launch of an installed release hashes the complete signed inventory, then records a stamp of the manifest and of the files' sizes, modification times and file IDs. Later launches with a matching stamp open without hashing. About a minute after the workbench loads, a background check compares that file metadata at most once a day and hashes the inventory again only when it changed. A failed check removes the stamp and reports the damaged resource.

## Known limitations and deferred work

The release target is Windows x64; signing status and platform/model acceptance belong to the exact artifact in [Validation](validation.md). Other WSL2 distributions and model endpoints need their own acceptance runs. MCP servers do not support OAuth sign-in, and there is no extension marketplace. Token counts before a request are estimates; the provider's reported usage replaces them after each request.

The [release validation record](validation.md) owns measured browser performance and acceptance coverage. Local OCR, PDF rendering and BPE run in the browser; individual acceptance cases do not establish document fidelity for every input or long-running OCR stability.

The count of 38 describes tool-package content, not the number of tools that passed functional acceptance. Command-line and offline-web checks are recorded per tool and artifact; the previous release's acceptance total does not apply to this expanded catalog. Native third-party GUI behavior, first-run prompts and actual UAC consent interaction require separate acceptance. Clean-Windows installation and restart results are recorded per artifact in the final acceptance record. Headless directory evidence uses an explicit bridge adapter and covers the directory interface. Per-tool acceptance remains separate from directory, installer and environment tests; the final validation record must identify the tested artifact and remaining cases.
