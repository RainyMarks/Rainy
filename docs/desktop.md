# Rainy desktop

English | [中文](desktop.zh.md)

Rainy is a lightweight AI workbench for office work, research and code on Windows x64. The interface is a native program (Rust and GPUI, `native/`) with document previews in the WebView2 that comes with Windows, and since 4.1 the Host is a Rust program too: Rainy ships no Node.js. The core installer includes the Windows Host. The editor's tools, Windows PHP and the Linux runtime base are optional components downloaded when needed; Strata local models and their weights are downloaded in Settings → Tools. The agent runs in the Host with the tools `read`, `write`, `edit`, `grep`, `glob`, the selected platform shell (`pwsh` or `bash`), `task`, the web and browser tools, plus the MCP tools the user enables. Projects run on native Windows, in a WSL2 distribution, or on an x86_64 Linux server reached over SSH.

The [Chinese installation and configuration guide](desktop-setup.zh-CN.md) owns the product workflow, configuration reference and source build instructions. [Validation](validation.md) distinguishes simulated providers from real API runs and records unresolved acceptance items. [Attribution](../THIRD_PARTY_NOTICES.md) describes the packaged dependencies and their licenses.

## How 4.0 differs from 3.x

- `RainyAgent.exe` (GPUI) draws the interface itself; there is no Electron or Chromium. The Host, the execution environments, the protocol and the user data are unchanged, so 3.x settings, chats, keys and projects carry over.
- The File, Edit and View menus of 3.x are now the project menu in the title bar and the command palette (F1 or Ctrl+Shift+P): every command this guide names as "File → …" or "View → …" can be found by name in the palette.
- PDF, Office, rich Markdown, the project map and the AI's built-in browser are shown in an embedded WebView2, with the same web code as 3.x.

## What 4.1 changes

- The Host is the Rust program `rainy-host` on every target: Windows, WSL and SSH servers. Rainy no longer contains Node.js; running and debugging your own JavaScript and TypeScript uses the Node.js installed on the target. Chats, settings, keys, projects and memory keep their formats, so 3.x, 4.0 and 4.1 read each other's data.
- The editor's language services and formatters are native programs: ty for Python, TypeScript 7's native compiler for JavaScript and TypeScript (language service and formatting), Ruff for Python formatting, and the installed clangd and clang-format for C and C++.
- [Strata local inference](#strata-local-inference) is back in Settings → Models.
- Each MCP server in Settings → Skills & MCP lists its tools with a switch per tool.

## What 4.5 changes

- Each model family gets its own agent's guidance, edit tool and plan tool, from `native/crates/host/src/agent/profile.rs` ([Per-model agent adaptation](model-adaptation.md)): GPT-5 and later edit with `apply_patch` and plan with `update_plan`, Gemini plans with `write_todos`, the others use `edit`, `write` and `todo_write`. Undo snapshots of `apply_patch` go by `<call id>#<n>`, one per file.
- Strata: without a Strata of Rainy's own, the one the person installed (`%LOCALAPPDATA%\Strata\terminal\<version>`, or the Control `components\control\active.json` names) is used with their own folders and is never updated or removed by Rainy. Model files the person has are set up in place: `strata models import <path> --plan` names the model, then `strata_install` gets `gguf_dir`.
- A downloaded update installs silently when Rainy quits (`--updated /S`, Rainy not started again; an installer that needs elevation waits for the next offer) unless `autoUpdate` in `desktop.json` is false (Settings → General → Automatic updates).

## What 4.4 changes

- Agent mode, a conversation-first layout, is the default when no layout was chosen; the buttons at the left of the title bar or Ctrl+Shift+A switch it with IDE mode, and the choice is kept per machine in `layout.json`.
- Reasoning effort follows each model's official levels, from the table in `native/crates/protocol/src/models/reasoning.rs` ([Reasoning levels](reasoning-models.md)); the new levels (minimal, medium, x-high) are stored in `thinkingLevel`, with `thinking` holding the nearest level older versions know.

## What 4.3 changes

- A new Settings → Tools page: Rainy ships no third-party tools; download what you need and uninstall it any time.
- On Windows the editor's tools are two optional components: the Python tools (`ide-python`: Ruff, ty and debugpy, about 26 MB) and the JavaScript / TypeScript tools (`ide-web`: TypeScript 7 and js-debug, about 11 MB). The Linux runtime still carries them.
- [Strata local inference](#strata-local-inference) moves to Settings → Tools and downloads Strata's newest release, keeps it up to date and recommends a model for the PC. Rainy no longer provides the Strata 0.1.39 runtime component.

## Offline installation and recovery

The [releases page](https://github.com/RainyMarks/Rainy/releases) provides the core installer. Each version's `v<version>-resources` release holds that version's PHP component and Linux runtime pieces. The [1.0.0 resource archive](https://github.com/RainyMarks/Rainy/releases/tag/v1.0.0-resources) still holds the Strata archive, the `environment/` WSL installation media and the `environment-components/` runtime archives. The core starts natively on Windows without WSL or scientific libraries. Source packaging restores the pinned inputs of [the input manifest](../toolpacks/build-inputs.v1.json) under `release/offline-<version>`.

Rainy 3.0 no longer includes the CTF tool catalog. Tools that earlier versions downloaded stay where they were installed, in the installation's `tools` folder or in `%APPDATA%\RainyAgent\native-tools`, and are no longer updated, repaired or launched by Rainy. Delete those folders if you no longer need the tools. Uninstalling the application preserves `runtime/` and user data.

New installations start on Windows; existing saved WSL choices are retained. Runtime settings list registered WSL2 distributions and can prepare an application-owned Ubuntu 26.04.1 environment from the external offline media. Creating WSL system components remains an explicit action, with administrator approval and a restart when Windows requires it. Existing distributions and their data are preserved. A missing saved distribution opens recovery instead of silently choosing another target. Clean-Windows administrator approval and restart recovery remain separate acceptance items.

## Optional components

The core installer does not contain the editor's tools, Windows PHP, the Linux runtime base (`linux-runtime.tar.xz`) or the offline Ubuntu development packages. The signed carrier resource `optional-modules.json` pins each component's archive, and the application downloads it on demand from GitHub release pieces into `%APPDATA%\RainyAgent\modules\<id>`. Each piece and the assembled archive are checked by SHA-256, interrupted downloads resume with HTTP Range requests, and cancellation keeps the downloaded pieces for the next attempt.

Settings → Tools downloads and removes the Python tools (`ide-python`, about 26 MB), the JavaScript / TypeScript tools (`ide-web`, about 11 MB) and PHP. The Host looks a tool up each time it needs it, so a download works at once and a removal is noticed: the status bar says which download a language needs and opens the Tools page, and formatting and debugging say the same. PHP serves the Windows native target; the code workspace section explains how a project chooses PHP. Strata is not one of these components; see [Strata local inference](#strata-local-inference).

WSL and SSH targets both use the Linux runtime, which comes in two layers. The base (the Linux IDE tools: Ruff, ty, TypeScript's native compiler, debugpy and js-debug; about 27 MB to download, 90 MB unpacked) is downloaded only when it changes, with progress on the startup page; the application layer (`rainy-host`, the viewer pages and small resources, about 11 MB) ships with the installer. An update with an unchanged base swaps in the new application layer and downloads nothing; on the first update to layered runtimes, an earlier runtime with the same content is reused as the base through hard links. Each version unpacks to `~/.rainy-agent/runtime/<application digest>/`, whose IDE tools link to `base-<content digest>/`. If the download fails, the dialog offers Retry, continue with Windows native, or Exit. Continuing with Windows native records Windows as the execution target, like a switch in settings. About a minute after a WSL start, the installed application deletes the runtimes earlier versions unpacked in `~/.rainy-agent/runtime` and bases no longer used, keeping this version's runtime, its base and any runtime a running process still uses. [SSH remote development](#ssh-remote-development) describes how a server receives the runtime.

About 60 seconds after startup, the packaged application deletes resources that earlier installers left in its `resources` directory: `strata-runtime`, `php`, `linux-runtime.tar.gz`, `native-tools-metadata.json`, `native-tools-download.json`, `native-tools-catalog.json`, `native-tools-channel.signed.json` and `native-tools-public-keys.json`.

## Application updates

The packaged app checks stable releases from `RainyMarks/Rainy` on GitHub at startup and downloads an available core update in the background. Help → Check for updates provides manual status and retry. A prepared update offers Later or Restart and install; installation starts only after confirmation, draft saving, and Host cleanup. A failed save keeps the app open. Ordinary exit does not install a downloaded update, and the updater does not select prereleases or downgrade the installed version.

Automatic updates replace the core application and preserve installed environments. They do not download WSL media or CPU/CUDA environment components again; the first WSL or SSH launch after an update swaps in that version's application layer and downloads the base only when it changed. CPU/CUDA environment components are still imported from matching offline release files. [Validation](validation.md) records the update checks completed for the published artifacts.

## Explorer integration

Both parts are off until you turn them on in **Settings → General → System integration**; until then Rainy writes nothing to the registry. When turned on, the installed app registers itself in the current user's registry (`HKCU\Software\Classes`), which needs no administrator rights; a development checkout run from source does not register. (3.9.0 turned both on by itself; 3.9.1 removes what 3.9.0 wrote until you turn them on again.)

- **Context menu**: "Open with Rainy" ("通过 Rainy 打开" in Chinese) on files, folders and the background of a folder. Windows 11 lists such entries under "Show more options".
- **Open with and default apps**: 80 extensions (Markdown, plain text, configuration files such as JSON and YAML, common programming languages, LaTeX and more) get a `Rainy.<extension>` file type, so Rainy appears under "Open with" for them, and Rainy is registered as an app Windows' Default apps can choose. A type that has no default app yet may then open in Rainy directly, since Rainy is the only app Windows knows for it. Windows does not let an app make itself the default; **Settings → General → System integration → Make Rainy the default app → Open system settings…** opens Windows' Default apps: Rainy's own page once Windows lists Rainy among its apps, and before that, right after registration, the Default apps page, where choosing a default for a file type such as `.md` offers Rainy.

Turning a part off removes its registry entries at once: Rainy's own keys and values only, and a key above them only when that left it empty and it did not exist before the part was turned on (Rainy notes which ones did, in `desktop.json`), so other apps' entries and your own keys stay. Changing the interface language updates the menu text. Uninstalling Rainy removes every entry; updates keep your choice.

Paths opened this way reach Rainy on its command line; when Rainy is already running, the new process hands them to the open window and exits. A folder opens as a project; a file opens in the deepest registered project that holds it, or with its folder as the project. On the WSL execution target paths are mapped into the distribution; on an SSH target local paths are not opened and Rainy asks you to switch the execution target first. Paths that do not exist are listed.

## Diagnostics

Rainy keeps the crash records of WebView2 locally and uploads nothing. Settings → General → Diagnostics → Export… saves a zip with the version and system information, the end of the execution Host log and of the Strata logs, and the five newest crash dumps, then shows it in its folder. Keys, tokens, passwords and the Windows user name are removed from the logs; settings, chats and API keys are never included. Errors, dialogs and menus follow the interface language chosen in Settings → General.

## Runtime contract

The Host ([architecture](architecture.md)) has no official accounts, telemetry, office runtimes, browser/computer control, schedules, multi-agent tools or plugin marketplace. One selected Host owns commands, terminals, model connections and sessions: on native Windows, in a WSL distribution, or on a Linux server over SSH. The Windows carrier owns the window and the shared project catalog. Lifecycle control uses stdin/stdout; authenticated HTTP/WebSocket carries application data. Target switching saves drafts and refuses running or queued Agent work, programs, debugging and terminals. New execution is frozen before the target preference changes, and Rainy restarts into the new target. The status bar shows the target, such as `Windows`, `WSL · Ubuntu` or `SSH · host`.

WSL and SSH startup wait for Windows-side loopback TCP reachability after the Host reports readiness. Connection refusal is retried within the original 90-second startup deadline; other connection errors fail startup. This check sends no HTTP request or authentication token. Cancellation, timeout and Host exit stop probing, and transport shutdown waits for the owned socket and child process to close. Native Windows startup has no cross-OS probe.

The window appears at once on a startup page that reports each preparation step. It reopens at the size, position and maximized state saved when it last closed; a first launch, or a saved position whose display is disconnected, centers the default size on the primary display and maximizes it when that display is smaller. A WSL target recorded by an earlier launch skips the environment check window: startup maps the carrier paths in one WSL call and unpacks the Host, and opens the check only when that target is unavailable. Each launch appends its phase timings to `host.log`.

Native window controls share the single top toolbar. Empty header space supports dragging and double-click maximization; editing and zoom shortcuts remain available. Unified settings separate models, context, project memory, skills, MCP and runtime controls. Runtime settings select the execution target, inspect existing interpreters, import release-approved offline components and manage SSH hosts.

New workspaces show files on the left and the main editor. Top-toolbar buttons reveal AI conversations and the bottom panel when needed; View → Focus editor hides both. Existing workspaces retain their saved pane visibility and widths. File actions occupy one row and editor actions share the open-tab row. Tight windows can show files over the editor. Editor tabs and conversations keep separate state. The homepage and About credit read `Developed by RainyMarks`. Active reasoning displays “Thinking...” in English and “思考中” in Chinese with the seconds so far, and a finished block reads “Thought for 12s”; the elapsed-time control uses the corresponding localized text. While a reply streams, the chat follows it; scrolling up by wheel, keyboard or scrollbar stops following at once, even in the middle of a smooth scroll, and Jump to latest output or scrolling back to the bottom resumes it. Enter and Escape that pick or drop an input-method candidate never send, rename or cancel. Empty views (no project, no open file, a new chat) show light rain in the accent color, and a click on their background makes a ripple; Settings → Appearance → Motion turns the rain off, and it stays still when Windows asks for reduced motion. The Rainy mark takes the accent color; its bars fall when pointed at and, in the top bar, while the current chat works. A reasoning block shows a rain cloud whose drops fall while the model thinks.

## SSH remote development

An SSH execution target runs the Host (agent, terminals, run and debug, language services and file access) on an x86_64 Linux server, while the interface stays on the PC. Rainy uses the OpenSSH client built into Windows (`C:\Windows\System32\OpenSSH\ssh.exe`), so `~/.ssh/config`, keys, ssh-agent and ProxyJump work as they do in a terminal. If the client is missing, add it in Windows Settings → System → Optional features → OpenSSH Client.

The server needs x86_64 Linux, `python3`, which installs and starts the backend, and a glibc new enough for Node 22. Nothing is installed system-wide: the runtime goes to `~/.rainy-agent/runtime/<sha256>`, and settings and chats stay in `~/.rainy-agent` on the server.

The first connection installs this version's Linux runtime, an archive of about 280 MB. The server first downloads it itself from the GitHub `v<version>-resources` release in verified pieces; the download resumes after interruption. If that fails, or is slower than 256 KiB/s after a minute, the PC downloads the archive and uploads it over the SSH connection. Every archive is checked against the SHA-256 pinned in the signed release. Later starts reuse the installed runtime; in testing the workbench appeared about 2 seconds after start. Runtimes of earlier versions are removed from the server in the background.

The Host listens on 127.0.0.1 on the server, and ssh forwards the same port number to 127.0.0.1 on the PC (`ssh -L`), so nothing listens on a public interface. A new server's host key is shown with its fingerprint in a Rainy dialog; a trusted key is added to `~/.ssh/known_hosts`, and a changed key is refused with an explanation. Passwords, key passphrases and one-time codes are asked in a small Rainy window. Answers are kept in memory for the current app run only and never saved.

Settings → Runtime environments → SSH remote development lists the hosts of `~/.ssh/config` automatically, together with hosts added in Rainy. Connect and add tests one connection (login, Linux x86_64 and `python3`) before saving the host. Switch to this host changes the execution target, and hosts added in Rainy can be removed. The execution target list in the same page also shows SSH hosts, and the command palette offers Connect to an SSH host…. Switching restarts Rainy into the new target, as for WSL.

On an SSH host:

- Folders open through the in-app folder browser; the Windows folder picker is not offered. Files dropped from the PC are not mapped to server paths.
- Prepare offline components points to installing tools on the server (apt, pip, nvm) and to Detect existing environments.
- The Strata local model on the PC is not reachable from the server; configure a model endpoint the server can reach. Model requests are made from the server's network.
- Model settings and API keys belong to each execution target. API keys are stored encrypted on the server, under a key the PC supplies on each run.
- Projects and project memory stay on the server; switching between the PC and a server does not carry projects across.

If the connection drops, Rainy reports that the connection to `SSH · host` was lost and offers Reconnect, which reopens Rainy; chat history remains on the server. A failed start offers Retry, Run on Windows instead, or Quit.

## Workbench

The AI pane holds chats with the agent, which reads and writes project files and runs commands under a per-chat permission mode (Model experience describes the modes). Files the agent changed are listed above the composer; opening one shows each change in the editor with Keep and Undo, and the auto-keep setting keeps pending changes when the next message is sent. The editor offers inline AI completion and Ctrl+K edits of a selection. The side pane holds files, search and replace across the project, and the Git panel, which can write commit messages with the chat model. The project map draws a project's parts and their imports, and the command palette reaches commands by name. Project memory, Skills (`.rainy/skills`) and MCP servers are configured in Settings. When a DeepSeek model in Settings has an API key, chats also get `web_search` (DeepSeek Search API, `POST /v1/tools/search`) and `web_fetch` (Fetch API, `POST /v1/tools/fetch`); the Host sends these requests through the proxy settings. Searching needs no approval; reading a page asks once per site in ask and read-only modes and can be remembered for the project as a `web_fetch:<site>` rule (removable in Settings → Security). Turn both off in **Settings → Models → Web search**. Add Folder attaches another root with its own stable identity, and cross-root file operations remain scoped by that identity. Windows projects use native paths; WSL projects use paths mapped and canonicalized inside the selected distribution; SSH projects use paths on the server. Existing workspaces retain their identity, editor recovery and source-target chats. Switching a project between Windows and WSL binds its public identity to the destination, restores directory mounts and selects that workspace before the Host is ready, while old chats and editor recovery remain in their original Host.

The editor provides multiple file tabs, syntax highlighting loaded per file type, search and replacement, go to line, undo, explicit saves and inline differences. File operations preserve UTF-8 BOM and line endings; a file with mixed line endings is saved with LF. Binary, non-UTF-8 and over-limit documents are read-only; the default editable limit is 5 MiB. Oversized UTF-8 previews retain up to 64 KiB without splitting a character.

Files the editor cannot edit open in a viewer. Images can be zoomed, panned and inspected pixel by pixel, and added to a chat with "Add to chat". Markdown opens in a WYSIWYG editor (Milkdown Crepe) and also offers source, preview and split; rich edits go to the same buffer and are merged into the file line by line against the serialization of the loaded text, so only edited lines take the editor's spelling. SVG switches between source, preview and a side-by-side split (Ctrl+Shift+V, Ctrl+K V); the Markdown preview follows unsaved edits and scrolls with the editor. PDF pages render on demand and their text, including hidden text, can be copied; CJK fonts a PDF does not embed use the bundled pdf.js character maps (`resources/pdfjs/cmaps`) and standard fonts. Word (.docx) is laid out by the page as paginated paper, with an "Office layout" switch; PowerPoint (.pptx, .ppt) and legacy Word (.doc) files are turned into PDF by the Microsoft Office or WPS installed on the PC in the desktop app (the bytes come through the Host, so files in WSL and on SSH servers work too), and without Office the text of each slide is listed. Spreadsheets (.xlsx, .xls, .ods) show as tables of up to 2,000 rows and 200 columns. "Open in default app" accepts document types only and is not offered for files on an SSH server. Office `~$` lock files say who has which document open, and `.lnk` shortcuts show their target, arguments and start folder. Audio and video play in the native player. Any file can be opened in the hex view, which pages through files of any size and offers go to offset (Ctrl+G), a data inspector, several copy formats and file type detection. GBK, UTF-16 and other non-UTF-8 text is shown read-only in a selectable encoding. Quick Open searches workspace paths with a bounded result list and reports truncation. Changing the query, switching projects, or reopening Quick Open invalidates earlier results; pending or failed searches cannot open an old result.

The Markdown rich view follows Typora's habits. The Outline side pane lists the document's headings, marks the one at the reading position (the caret line in the source view) and jumps to any of them. Ctrl+F / Ctrl+H open find and replace; matches run across bold and other marks but not into code blocks, case can be matched, and Replace all is undone in one step. Pasted or dropped images (up to 25 MB each) are saved through the Host to an `assets` folder next to the document, a "name.assets" folder or the document's own folder (**Settings → General → Markdown**), with a `-1` style suffix when the name is taken, and the document gets a relative link; screenshots from the clipboard are named by time. Math blocks and Mermaid diagrams show only their rendering until clicked, then their source with a live preview; Mermaid loads on demand and renders at its strict security level. YAML (`---`) or TOML (`+++`) front matter gets its own text box at the top. Shortcuts: Ctrl+0–6 for paragraph and headings, Ctrl+= / Ctrl+- to change the heading level, Ctrl+T for a 3×3 table, Ctrl+Shift+K code block, Ctrl+Shift+M math block, Ctrl+Shift+Q quote, Ctrl+Shift+[ / ] ordered and bullet lists, Alt+Shift+5 strikethrough, Ctrl+Shift+` inline code, Ctrl+K link and Ctrl+/ for the source view; Ctrl+click on a link hands web and mail addresses to the system, opens project files in the editor and jumps to `#heading` targets in the document. F8 focus mode fades everything but the current block, and F9 typewriter mode keeps the caret line in the middle of the view. The status bar counts words (each Chinese, Japanese or Korean character is one word), with characters and reading time on hover. File → Export as PDF… / Export as HTML… writes a self-contained page with highlighted code, math (MathML), Mermaid diagrams (SVG) and local images (data URLs) embedded; front matter is not printed and web images keep their links. PDF is printed to A4 in a hidden window with scripts disabled, with bookmarks and accessibility tags; Chromium's ToUnicode maps name the Kangxi radical for ideographs that share its glyph (such as 二 and 文), and the export rewrites them to the NFKC ideographs in an incremental update so copied and searched text matches the document (`native/crates/app/src/web/pdf_text.rs`; a hidden WebView2 prints the PDF). The save dialog starts in the document's folder (Documents for SSH projects).

Language services receive Host file URIs. The editor matches the URI spellings servers return, such as an encoded drive colon or a different letter case on Windows, to the same file, including Windows drive roots and UNC shares.

Recovery storage keeps dirty buffers, open tabs and pane geometry under each workspace. An external edit refreshes a clean buffer; a dirty buffer retains its text and offers a comparison. Version conflicts stop saving until the user resolves the displayed difference. Run and debug save every changed file in the current workspace and stop when a save fails.

Persistent language servers analyze unsaved editor documents: ty for Python, TypeScript 7's native compiler (`tsc --lsp`) for JavaScript/TypeScript, and clangd for C/C++. Completion, hover, signature help, diagnostics, go to definition (F12), references (Shift+F12) and rename (F2) come from these servers; rename also edits files that are not open, which then appear as unsaved tabs. Formatting uses the bundled Ruff for Python and TypeScript's own formatter for JavaScript and TypeScript, or the prepared clang-format. Python interpreter choices and CMake compilation databases also configure editor language services. Selected code is sent through a normal recorded user message containing its path, range and text.

The run button runs the open file with the language its extension implies. The menu beside it chooses another language for that file, which the workspace remembers, or pins a saved configuration for another entry program; saving the open file's configuration does not pin it. Run configurations retain the entry, arguments, interpreter or compiler, working directory and CMake choices per workspace. Python supports files, modules and existing virtual environments; JavaScript and TypeScript use the Node.js installed on the target (Rainy does not ship one); PHP supports direct script runs; C/C++ supports single-file and CMake builds. Failed builds stop launch. Debugging uses debugpy, js-debug, CodeLLDB on Windows and GDB DAP on Linux for workspace-launched programs. The interface exposes breakpoints, stepping, stacks, variables, watches and stop. External process attachment and PHP debugging are unavailable.

Runtime discovery inspects project virtual environments, Conda registrations, common Python locations, PATH and imported components without installing packages into them. A selected interpreter configures project tools, terminals, runs and language services through a process-local environment. Executable readiness and library capabilities are reported separately; a working Python can lack PyTorch or CUDA. Interpreters from the other execution platform are rejected. Settings → Tools downloads PHP 8.5 with the json, openssl, mbstring, pdo_sqlite, curl and zip extensions for native Windows targets. Until it is downloaded, running a PHP file on a native Windows target reports where to download it; the run configuration can instead select an installed `php.exe`. An installed environment component or a project's selected PHP takes precedence. WSL and SSH targets use the PHP installed on that Linux system.

Offline components provide isolated Python 3.12, Node 24, Windows PHP, native C/C++ tools, and separate CPU or CUDA scientific environments. Scientific components include NumPy, SciPy, pandas, scikit-learn, image processing, Jupyter and common deep-learning libraries, with matched PyTorch 2.11, torchvision 0.26 and torchaudio 2.11. Import verifies the release catalog, archive and file inventory before selecting a content-addressed generation. Existing user environments and global PATH are unchanged. CUDA needs a compatible NVIDIA driver. The Ubuntu 26.04 amd64 development wizard downloads its verified C/C++, GDB, CMake, clangd and PHP packages (about 165 MB, the release's `linux-dev-packages` component) when you click Install, installs them with apt's own downloads disabled, and deletes the download afterwards.

The desktop permits clipboard text writes from its authenticated Host origin. Stored chats show each tool call as a terminal, read, diff or generic card by tool type.

<a id="strata-local-inference"></a>
## Strata local inference

Strata ([Niko1221/Strata](https://github.com/Niko1221/Strata), MIT license) is downloaded on demand in Settings → Tools → Strata local models; Rainy does not ship it. Download reads the install manifest of Strata's newest release, downloads the Strata Terminal it lists, checks it against the manifest's SHA-256 and GitHub's digest and confirms it with Strata's signed feed, then lets `strata update` install the inference engine for this PC's graphics card. The feed is checked about 45 seconds after start and every six hours, and Strata updates itself when no model runs (this can be turned off); Check for updates checks at once.

The model list comes from Strata's own catalog (the management server Strata's app uses): every size of every model shows its download size, the memory it needs and whether it fits, fits slowly or does not fit on this PC, and the size Strata recommends for this PC's memory and VRAM is marked. Downloads show progress, can be cancelled and continue next time, come from Hugging Face or ModelScope, and go to a `Strata-data` folder on the roomiest non-system drive unless another folder is chosen. A downloaded size can be started and deleted.

Start loads the model through `strata launch`; Strata picks the context length for the model and PC unless one is fixed, and the port is 8080 by default. Connect and set as default asks the selected Host to verify the loaded model and context before saving the local endpoint. Rainy stops only servers it started; a Strata server started elsewhere is shown as such. Strata runs on Windows even when the project Host is WSL; if WSL NAT cannot reach Windows loopback, select the Windows target for Strata. A Host on an SSH server cannot reach Strata on this PC.

All of Strata's files except the models live in `%APPDATA%\RainyAgent\tools\strata`. Every Strata process gets its folders there and a writable temporary folder with an ASCII path, inherits no credential-like variables or outside Python settings, and ends with Rainy. Uninstall removes the folder and, if asked, the downloaded models. The Strata component of 4.1–4.2 (`modules\strata`) and its cache can be deleted from the card.

This release checked download, verification, engine install, a model download, start, chatting through the connection and stop on a real RTX 5090 laptop GPU; other GPUs and AMD cards are not yet tested. [Validation](validation.md) records the tested artifacts and what remains.

## Model experience

Each request is estimated before it is sent: system prompt, tool declarations and messages. When the provider reported more input tokens than estimated for one of the chat's last five requests, estimates grow by that ratio plus 10%; an older difference no longer counts. The composer's context meter shows that estimate, or the usage the provider reported for the last request. When the estimate reaches the compaction threshold, an older span of the chat is replaced by a summary. The span never includes the latest user request and never separates a tool call from its result. The summary is written by the chat's own model. While the previous request's prompt cache is warm (the request started less than 54 minutes ago with the same model and reasoning level), the summary request repeats that request unchanged and adds one instruction, so it is billed mostly at the cache-read price; otherwise, or when the model calls a tool instead of answering, a separate request summarizes only the span. Opening a compaction line in the chat shows which request was used and its input, cache and output tokens. The summary keeps user instructions that still apply, quoted exactly, and records verified progress, exact paths, errors, unresolved work and the next action; instructions found in files, tools or web pages are recorded as data, not as tasks. The model sees the summary as a checkpoint written by the assistant, not as a user request. A context-overflow error compacts and retries once; `/compact` compacts on request. A request that fails for a passing reason (the provider is overloaded or rate-limits, the connection drops, or the model stops sending) is retried up to three times, after about 5, 10 and 20 seconds or after the delay the provider asks for; the chat counts down with Retry now, and Stop ends the wait. Refused requests (a wrong key, an exhausted quota, an invalid request) are not retried. When the retries are used up, or after any failed or stopped request, Retry on the error asks the model again without resending the message. Failures the chat got past shrink to one line, so a recovered turn is not a column of red boxes. A failed summary leaves the history unchanged. Explicit output limits, including the DeepSeek preset's maximum, take precedence over defaults.

Requests to one endpoint origin share a queue in arrival order. A loopback server (Base URL host localhost, `*.localhost`, 127.0.0.1 or [::1]) runs one request at a time; any other endpoint runs up to four, so parallel chats and background requests do not wait for each other's complete streams. A stream that sends nothing for five minutes is aborted, and one request may run for at most 30 minutes.

Settings → Models → Network proxy chooses how model requests reach the service: Follow the system (the default), No proxy, or a Manual HTTP proxy address such as `127.0.0.1:7890`, optionally with `user:password@`; SOCKS proxies are not supported, and a saved password is shown as `***`. Following the system, the Windows Host asks for each service which proxy Windows uses, so proxy settings, the bypass list and PAC scripts apply; changes take effect within 30 seconds. In WSL, Follow the system uses the `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY` variables WSL passes to the Host; shell profiles such as `~/.bashrc` are not read, so choose Manual to use a proxy there. Test connection reaches the selected model's Base URL with the choice before it is saved. Model discovery and MCP servers over HTTP use the same proxy, and MCP servers that failed connect again when the setting changes. Loopback, private-network, `.local` and single-label addresses such as `gpu-box` always connect directly; commands the AI runs and terminals are not proxied.

Settings → Models → Global prompt saves instructions, at most 4,000 characters, that every chat's system prompt includes, including chats already open. Compaction summaries, project memory and connection probes keep their own prompts; an empty prompt adds nothing.

Model settings live in the selected Host's `settings.json`. API keys live in its `.credentials.sealed.json` (mode 0600), encrypted with a key that Windows data protection (DPAPI) keeps for the signed-in Windows account, and an environment variable with the same name takes precedence. Keys saved by an earlier version are encrypted at the first start; if Windows can no longer open the key, for example after an administrator reset the account password, stored API keys must be entered again. New API models default to OpenAI Responses and local models to Chat Completions; the defaults remain editable to match the service. The model list shows saved configurations first, a saved preset under its preset name, then the presets not saved yet; Load copies a preset into the form. The DeepSeek preset uses 1,000,000 context tokens. A model's "Accepts images" switch decides whether images can be sent to it and whether the agent can take screenshots of pages: Claude models take images unless it is turned off, other models only when it is turned on, and the DeepSeek preset turns it on. A service that does not take images fails the request. Both Claude presets share the Anthropic key, offer only the reasoning levels the model accepts, and keep the prompt cache for an hour. Model discovery requires only a provider, Base URL, protocol and optional request key; it saves nothing. Saving and the separate streaming/tool-call check require the complete model configuration. Rainy never silently substitutes another model. On first start, models, keys and the global prompt of a 1.x profile are imported once; 1.x chats are not.

Skills are folders with a `SKILL.md` under `<project>/.rainy/skills` and `~/.rainy-agent/skills`. Only their names and descriptions, at most 4,096 tokens together, enter the system prompt; the model reads a skill's file when it needs it. MCP servers are configured once in Settings → Skills & MCP and serve every chat over stdio (command, arguments, environment) or HTTP (URL and request headers such as `Authorization`); an HTTP server that refuses Streamable HTTP is reached over the older HTTP+SSE transport. **Import JSON** reads the MCP configuration of other apps (Claude Desktop, Claude Code, Cursor, VS Code, Windsurf, Cline, Zed, Gemini CLI, opencode, Continue, Cherry Studio and others) or the snippet from a server's page, pasted or from a file, shows what each server will run (secrets hidden, scripts written into the arguments shown in full and pointed out) with notes on placeholders and fields Rainy does not use, leaves out servers identical to configured ones, and adds the checked servers without replacing existing ones; MCP JSON pasted into a new server's form opens it too. Environment values and headers are stored in `settings.json`, not in the credential store that holds model keys. Their tools appear as `mcp__<server>__<tool>`, calls time out after 60 seconds, and server instructions join the system prompt.

Each chat has a permission mode, chosen beside the composer: Read-only reads and searches files; Ask (the default) reads and writes inside the project but asks before commands, MCP tools and writes outside the project; Full auto asks nothing. Always allow remembers a simple command prefix or MCP tool per project, listed in Settings → Security. Write and edit keep the replaced content (files up to 16 MiB), so one change or a whole turn can be undone unless the file changed since; changes made by commands are not covered. The grep and glob tools search with ripgrep. The read tool pages lines, by default 2,000 lines, 2,000 characters per line and 50 KiB; its long-line marker is explicit and the file stays intact. Write and edit require a prior read of an existing file and keep its BOM and dominant line ending. Shell commands (`bash` on WSL and SSH targets, `pwsh` on Windows) time out after 60 seconds by default and 10 minutes at most. Rainy does not ship PowerShell: `pwsh` runs PowerShell 7 from the Windows basic component, Program Files or PATH, and otherwise the Windows PowerShell 5.1 built into Windows, which the system prompt names because it lacks `&&` and `||`; long output keeps its head and tail in the reply and the full text in a file under the Host temp directory. Workspace instructions (`AGENTS.md`, `CLAUDE.md` and their `.local` variants, at most 64 KiB) enter a chat once before its first request, and instructions of subdirectories the agent works in are added when it reaches them. Chat titles use the first user message.

## Project memory

Project memory uses the carrier project identity across execution targets. Windows and WSL share the project record; environment-specific notes retain their target scope. An SSH Host keeps its projects and project memory on the server. Use and automatic generation have independent switches. Automatic generation costs model requests, so it starts off for new projects; projects that already have a memory record keep their setting. Human edits require the displayed revision, and generated updates cannot replace or remove a manually corrected note. Deletion retains source watermarks and exclusion hashes so old evidence does not recreate a removed note.

After a completed turn, generation waits for 60 seconds without foreground work and runs at most once per project every 10 minutes. It uses the selected model with no tools, at most 4,096 input tokens and 512 output tokens, a 30-second timeout, and no automatic cloud fallback. New foreground input cancels the auxiliary request. At most 1,024 estimated tokens of active notes are stored; new chats receive at most 512 tokens and 5% of their input budget, including recall framing. Failed, cancelled or stale-revision generation preserves the prior record. Recall enters the chat as a context entry marked as historical data, so later requests replay it from the chat file. Source file changes invalidate dependent generated facts; original session logs remain available.

The production carrier authenticates its resource inventory using a public release key embedded at build time. A failed check removes the stamp and reports the damaged resource.

## Known limitations and deferred work

The release target is Windows x64; signing status and platform/model acceptance belong to the exact artifact in [Validation](validation.md). Other WSL2 distributions and model endpoints need their own acceptance runs. SSH targets require an x86_64 Linux server with `python3`; other architectures and operating systems are not supported. MCP servers do not support OAuth sign-in, and there is no extension marketplace. Explorer integration uses the classic context menu, which Windows 11 lists under "Show more options"; Markdown exports to PDF and HTML only, not to Word. Token counts before a request are estimates; the provider's reported usage replaces them after each request.

The [release validation record](validation.md) owns measured browser performance and acceptance coverage. PDF rendering runs in the page; individual acceptance cases do not establish document fidelity for every input.
